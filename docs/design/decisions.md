# Decisions

A record of the calls Better-Cal makes where two or more readings were each defensible and one had to be codified, so any of them can be revisited later without digging through commits or reviews. Started 2026-11-04; revised the same day after an outside review of the first draft.

Each entry carries a status, because "we chose this" and "the code does this" are different claims:

- **Standard:** the standard says it; we follow it.
- **Deviation:** the standard says otherwise; we depart on purpose, and say what it costs.
- **Choice:** the standard or the situation leaves it open; we picked.
- **Workaround:** what the code does because of a constraint (a library, a storage shape), not because it is the ideal reading; kept until the constraint goes.
- **Defect:** the code does this and shouldn't; its repair is scheduled, which is a release decision, not a reading.
- **Planned:** decided, not yet built.
- **Open:** undecided.

And each says whether it is verified: by which check, or not yet. What doesn't belong here: visual design choices, which keep their own records ([calendar marks](calendar-marks.md), [day marks](day-marks.md)).

Two principles behind most of the entries. A change previews its consequences and offers the reasonable readings as choices. And a preselected reading avoids silent deletion, unexpected detachment and the overwriting of a deliberate exception, while every addition and every changed bound is shown plainly; preserving a count and preserving intent are different things, and no default guarantees the latter.

## Repeating Events and the Standard

- **A clock time the spring change skips, for any spelling of the rule.** Status: deviation. Chosen: the occurrence is kept that day, at the same clock plus the gap (02:30 becomes 03:30), and later days are at their own clock. The standard's 3.3.10 says a generated instance at a nonexistent time "MUST be ignored and MUST NOT be counted"; its 3.3.5 rule for a single date-time (the offset before the gap) is what we apply to every generated instance. Why: a weekly event that vanishes one week a year is worse than one an hour later. Cost: a strict client reading the app's ICS may leave that day out and end a COUNT series an occurrence later. One rule for every spelling: a plain DAILY, a rule naming its hour in BYHOUR, and a rule listing all seven weekdays express no different intention, since another calendar or serializer picks the spelling. The app's own expander (1.5.0) applies the one rule with no state carried between days, for every interval and from any window; until then a BYHOUR rule omitted the day and a rule listing weekdays kept the shifted clock for the rest of the series (the library's readings, [#201](https://github.com/Oshyan/better-cal/issues/201)), and migration 064 moves the keys those readings wrote. Verified 2026-11-04: the expander's hand-listed tests (`server/tests/expander.php`, "Gap:": five spellings, a monthly and a yearly rule, a half-hour gap, two windows and the model reading the same keys), and the migration's database test; the harness's evaluator still reads the library's two gap readings and is updated by its owner. Verified 2026-11-05 from windows far from the start ([#201](https://github.com/Oshyan/better-cal/issues/201)): `server/tests/expander.php`, "Far windows (#201)", hand-listed, a short and a long window, a year and nine years from the start, across the gap day, for daily, weekly and monthly rules with and without BYHOUR; the issue's own reproduction is "a daily weekday list, April 2028, short and long". Where: [series model](series-model.md#zones-dst-and-all-day-days). Chosen 2026-11-02 for plain clocks, extended to every spelling 2026-11-04 on review; built 2026-11-04.
- **A clock time the fall change repeats.** Status: standard, with a choice on top. Chosen: a wall clock given with no instant is its earlier instant, as 3.3.5 says; an instant given stays that instant; the plan's note says which of the two the series is at and what the zone data says of it. Else: the later instant (what PHP reads a repeated wall clock as, and what the library's monthly and yearly steps gave a later year's day before 1.5.0, whose keys migration 064 moves). Verified: the harness's second-fold case and the fold mutation, with the model's unit tests and the expander's ("Fold:", 2026-11-04). Where: series model, same section; the `fold` and `daylight` fields of a note in the [contract](../api-contract.md). Settled 2026-11-02; the note's data 2026-11-04.
- **A start that would fall in the skipped hour.** Status: workaround. The code stores the series one period earlier, on the rule's latest day before it where the clock exists, as a generated skip with COUNT raised by one, and every sentence names the first day shown. Why a workaround: storage holds one instant and the expander takes every day's clock from the start, so a start stored at the shifted clock would move the whole series an hour. The ideal is a start that is the day the person named; that needs storage of the clock apart from the instant. Every count a person sees is the events shown: the API's rule says the shown COUNT and a COUNT sent is the shown one, the writer adding the stored day back (was, until 1.5.1: the editor's "Ends after" showed one more than the events shown, [#202](https://github.com/Oshyan/better-cal/issues/202)). A start typed into the skipped hour reaches the server as the clock typed (`typed` in the contract), so a new series typed there is stored by this same rule (was: the server received the shifted instant and stored a series an hour later). Verified: the harness's anchored-start cases; 2026-11-05, `server/tests/series-model.php`, "Typed clock:" and "Ends after:", and the smoke test "quick add typed clock". Where: series model, same section. Settled 2026-11-02; count and typed clock 2026-11-05.
- **HOURLY across a skipped hour.** Status: choice. Chosen: the walk steps by wall clock, so an every-3-hours series reads 00:00, 03:00, 06:00 on the change day and keeps its pattern after; a skipped wall clock resolves by the offset before the gap. Else: elapsed time (00:00, 04:00, 07:00 that day), under which the series' clocks shift by the change until the next change shifts them back. Why: a rule in hours names clock positions a person reads off a day, like a daily rule does. A rule in minutes or seconds is different on purpose: its periods are stepped in elapsed time from the start's own, as the standard's table reads them, so `FREQ=HOURLY;INTERVAL=3` and `FREQ=MINUTELY;INTERVAL=180` are not the same rule here. That distinction is the weakest-argued entry in this record: it rests on how people write the two, not on the standard, and only imports write minute rules. Verified: the harness's evaluator steps the wall clock since c74c57a, with a spring and a fall example in its hand-listed set, and the expander's tests list the spring and fall days of an hourly and a minute rule side by side ("HOURLY:", "MINUTELY:", 2026-11-04); the earlier revision of this record claimed agreement before the evaluator had it. Where: `tools/edit-harness/README.md`, series model. Settled 2026-11-04.
- **An instant the walk reaches twice.** Status: standard. A wall-clock step that resolves onto the next step's instant (an hourly rule's step to the skipped 02:00 resolves to 03:00, and the next step is 03:00) yields that instant once and counts it once: 3.8.5.3 says "Duplicate instances are ignored." Stated once in the walk, for every frequency. Verified 2026-11-04: `server/tests/expander.php` and the harness's hand-listed examples through the window expander, which is where the duplicate was found. Settled 2026-11-04.
- **A set position on a day whose clocks merge.** Status: standard. A period's set is its instants: its local times are resolved (a skipped clock by the gap rule above) and two that land on one instant are one member, and BYSETPOS counts positions among those instants, positive from the first and negative from the last, for every frequency. So `DAILY;BYHOUR=2,3;BYMINUTE=0,30;BYSETPOS=3` has no occurrence on Los Angeles' spring change day, whose four clocks are two instants (03:00 and 03:30). Else: the position taken among the nominal clocks before they resolve (03:00 that day), which the harness's evaluator read for date frequencies while its hourly path and the expander resolved first. Why: an occurrence is an instant and 3.8.5.3 ignores duplicates, so a clock merged into another holds no position of its own. Verified 2026-11-04: the harness's hand-listed examples (positive and negative positions, with and without a collision), its fixed case, and the mutation that restores the other reading in the expander. Where: `tools/edit-harness/README.md`, The Oracle. Settled 2026-11-04.
- **A rule naming its hour in a zone whose clocks move by half an hour.** Status: defect, fixed in 1.5.0. Read from the start the library's hour-by-hour stepping drifted the minute (03:00 became 03:30 after the change); read from a later window it didn't; keys were stored by the from-start reading. The app's own expander expands clock parts by the standard's table, as wall clocks of each day, so 03:00 stays 03:00 from any window, and migration 064 moves the keys the drift wrote. Verified 2026-11-04: the expander's test "Clock parts: 03:00 by BYHOUR stays 03:00 after a half-hour change", and the half-hour gap in "Gap:". Where: [#202](https://github.com/Oshyan/better-cal/issues/202). Deferred 2026-11-04; fixed 2026-11-04 for 1.5.0.
- **COUNT and the days that are not shown.** Status: standard. Two different things: a day the person skipped (an EXDATE) is one of the N, since the rule generates its set, COUNT bounds that set, and exclusions are taken out afterwards (3.8.5.1's construction); a generated instance the rule can't place (30 February) is not an occurrence and is not counted (3.3.10). Under "keep N events" the count is raised for each skip the change itself generates, never for one the person made earlier, because that was a choice about that day, not a request for one more at the end. Verified: the harness's bound checks and the COUNT mutation, and the expander's "COUNT:" tests (the 31st three times, a skip one of the three). Where: series model, Bounds. Settled 2026-11-02; the wording corrected 2026-11-04.
- **Where a series starts.** Status: choice. Chosen: on a day of its rule; a start the rule doesn't name moves forward to the rule's first day, keeping the time, and the editor says so. The standard's 3.8.5.3 says a start not synchronized with its rule gives an undefined set, so there is no standard reading to follow. Else: keep the typed start as a first occurrence outside the pattern, which some calendars do. Why: one reading everywhere; a stray first day confuses every later edit. Verified: the creation tests in the PHP suite. Where: contract, event creation. Settled in 1.5.0.
- **Minute and second rules.** Status: choice (was: workaround, while the library's iterator, which has no step for them, expanded the other frequencies). They are rows of the app's own expander like any other: periods stepped in elapsed time from the start's own minute or second, BYSECOND expanding a minute, every other part limiting, as the standard's table reads them. Verified 2026-11-04: the model's unit tests, the harness's evaluator, and the expander's table tests (every SECONDLY and MINUTELY cell). Where: series model, "The expander is the app's own". Settled 2026-11-02; a choice from 2026-11-04.
- **A rule part invalid for its frequency.** Status: deviation. Chosen: a rule carrying a part the standard's table marks N/A for its frequency is one the expander can't read: refused where a rule is written, edited only by field. 3.3.10 says such parts "MUST be ignored". Why: a rule read with a part dropped means something the person didn't write, and an imported one keeps its text for the next client. Verified: the PHP suite's refusal tests, and the expander's (every N/A cell of the table refused by the expander and by the writer's check, 2026-11-04). Where: series model, same section. Settled 2026-11-02.
- **A walk that can't complete.** Status: choice. Chosen: a rule has ended when the walk has gone round the calendar's 400-year cycle together with the rule's interval phase without an occurrence, since from there it would only repeat (an interval of 401 years still finds its year; the cycle is the calendar's and the phase's together). Any other limit of the walk (a search budget) is an error the plan reports as a rule it can't read, never a series that ends there. Else: stop silently after a fixed number of tries, which 1.5.0's first candidate did, and which cut a leap-day series to one event while its check agreed. Verified: the harness's sparse cases and the count-cap mutation; the evaluator reports its own horizon as incomplete rather than ended; the expander's "End:" tests (no 30 February, an unreachable hour, 401 years, year 9999, and a walk limit reached as an error). Where: `server/src/Domain/Series/RuleIterator.php`. Settled 2026-11-04.
- **The expander is our own.** Status: choice, built for 1.5.0. Chosen: one expander written from the standard's table (`Series\RuleIterator`), read by the window, the model, the occurrence check and mail admission, with the library kept for reading and writing iCalendar text and for the CalDAV server. Why: the library's iterator ignores BYSETPOS outside MONTHLY and YEARLY, BYMONTHDAY on DAILY and every BY part on HOURLY, places a BYWEEKNO Sunday a week early, yields a phantom occurrence at an UNTIL past a month's end, and loops on a rule with no day; every fix so far was a patch around it, and the patches are where this release's caps came from. The start is always the first occurrence, an UNTIL before it bounding only what the rule generates (3.8.5.3's set is built from DTSTART). The harness's evaluator is a separate writing of the same table and stays the check. The CalDAV server reads it too, from 1.5.1: a calendar-query's time range on VEVENT is answered from the occurrences the window shows (its gap days, repeated hours, skips and edited days) under RFC 4791 9.9's table, an object passing the library's validation for every other part of the filter as well, and an `expand` request (9.6.5) on calendar-query or calendar-multiget is served from the same occurrences ([#202](https://github.com/Oshyan/better-cal/issues/202)). What still reads the library's iterator: a free-busy-query's busy times (which objects it reads is the expander's), a calendar-query sent with Depth 0 to one object without expand, and a time range on an alarm or a property; clients expand the objects themselves, so what they show is theirs. Verified 2026-11-04: `server/tests/dav-query.php`, hand-listed, each row of 9.9's table and a series' edited, skipped, gap and all-day days through calendar-query and expand. Verified 2026-11-04: `server/tests/expander.php`, one hand-listed case for every cell of the table (RFC 5545's own examples among them) and every reading in this section, with the PHP and database suites and the harness. Verified 2026-11-05 that mail admission's estimate of whether a series is still active reads the rule's BY parts through this expander ([#202](https://github.com/Oshyan/better-cal/issues/202)): `server/tests/mail-security.php`, "mail capacity: a weekday list, BYHOUR, a minute rule limited by its hour and a plain rule are active through their last occurrence and no longer". Decided 2026-11-04; built 2026-11-04.

## Edits to a Series

The [series model](series-model.md) is the full statement; these are its judgment calls.

- **A drag is measured against the occurrence as it shows.** Status: choice. Every part of a drag is a delta from the occurrence as it shows, its own values where it owns them, never an absolute value passed through, because a person drags what they see. What this does not settle: a value typed into the editor. Setting an exception's 19:30 to 20:00 for all events can mean "shift the series half an hour" or "make the series 20:00", and a length typed has the same two readings; 1.5.0 reads both as deltas; from 1.5.1, from a day that owns the field, assignment is the adoption reading beside the delta, by operation and by field: a time, adopted first for a drag and a typed value alike; a length, adopted first when typed (`typed` in the request), the delta first for a resize; a day, by the period threshold either way. Where the day doesn't own the field the two readings are one plan. Verified: the harness's oracle for drags; 2026-11-05, `server/tests/series-model.php`, "Adopt, length" and "Adopt, case 14". Where: series model, Changing the Series from an Edited Day; [#202](https://github.com/Oshyan/better-cal/issues/202). Settled 2026-11-02 for drags; typed values 2026-11-05.
- **A sent rule equal to the stored one is no rule.** Status: choice. Lists compare as sets, INTERVAL=1 is dropped, WKST counts only where the standard makes it count, a bare rule equals its one-member form. Why: an editor round-trip must not read as a change. Verified: the PHP suite. Settled 2026-11-02.
- **Written, not inferred.** Status: choice. "Every 31st" stays `BYMONTHDAY=31`, never rewritten into the last day, and a reading picked in the dialog is written in its own form. Why: what the person wrote is what the editor shows them next time. Verified: the harness's shape check. Settled 2026-11-02.
- **A drag on the 29th to 31st: which reading first.** Status: choice. "On the 30th, or the last day in shorter months" preselected; "skipping months without one" second; a day counted from the end keeps counting from the end first. Else: skipping first, which is what other calendars do. Why: it keeps every month's appointment; it also adds one in months the skipping reading had none, which the row says. Settled 2026-11-02.
- **A list member dragged to another weekday.** Status: choice. "Move every Wednesday to Thursday" preselected over shifting the whole pattern. Settled 2026-11-02.
- **A day moved on its own, when the timetable changes.** Status: choice. It stays where it was moved. Settled 2026-11-02.
- **Changing every event from an edited day.** Status: choice, built for 1.5.1. Each part the day owns and the change moved (its date, time, length) is a group: adopt it as the series' own, or move the series the same way and keep it the day's (1.5.0's reading). Adopting the day is preselected when it moves every event by less than one period of the rule's frequency, the same way first when it is a period or more; adopting the time always. The period is the frequency's as written, never the family's: a DAILY list (Mondays and Wednesdays written DAILY) repeats daily, so its period is a day, where a WEEKLY list's is a week (was: the family's week for both, found by the edit harness, fixed 2026-11-05, `server/tests/series-model.php`, "Adopt, by frequency"). An adoption that would be refused is disabled and never preselected; the same way is then the selection. The threshold is a weak signal (a small change across it flips the default) and stays a judgment; what has to hold is that each choice shows its concrete schedule and the selection is explicit. Verified 2026-11-05: `server/tests/series-model.php`, "Adopt, case 12/13/14/21" and "Adopt, apart", and the smoke test "adoption:" for the dialog's words. Where: [#202](https://github.com/Oshyan/better-cal/issues/202), series model. Settled 2026-11-02, built 2026-11-05.
- **A day the new rule gains at an edge.** Status: choice. Left out by default, as a generated skip, with "Add it" offered. Why: nothing appears the person didn't ask for. Settled 2026-11-02; preselection moved after the fourth review.
- **A count that would end before the day dragged.** Status: choice. "Keep the end" preselected, the dragged day staying in the series, and the row says the count grows; "keep N events + this one on its own" offered. Settled 2026-11-02; preselection moved after the fourth review.
- **A bound the person sent that cuts off the day acted on.** Status: choice, built for 1.5.1. The Day Acted On Comes First is a rule for drags, where the destination is the person's intent, so a kept count that would end before it is rewritten to keep it. An UNTIL or COUNT typed into the editor is the person's own statement, so a day acted on that it cuts off is an ordinary day outside the bound: it takes the outside group's choice, kept as an event of its own where it was put (preselected, as for every day outside) or deleted, and has exactly one outcome in the plan. Each day's outcome comes from one function in the model, so no day is in two of the plan's lists. Was: the day acted on was always kept on its own, and with "Delete" chosen for the other days outside it was both detached and deleted (found by the edit harness on a week-number rule). Verified 2026-11-05: `server/tests/series-model.php`, "Sent bound (weekly)" and "Sent bound (week number)", and `server/tests/db/series-plans.test.php`, "a bound sent from an edited day that cuts it off", each choice committed and undone. Settled 2026-11-05.
- **Scopes a calendar kind cannot take are not offered.** Status: choice, built for 1.5.1. A scope the server refuses for every occurrence of a kind of calendar is left out of every chooser (the delete, answer and new-time rows, the drop chip after a drag, resize, reschedule or a calendar or person drop, and the editor's Apply to), which all read one function, `seriesScopes` in `web/src/app/scopes.js`; where it leaves a scope out the chooser says why in one line, taken from `planwords.js` beside the refusal panel's own sentence for the same code, so the two cannot drift. On a Google calendar that leaves out "This and following" until 1.5.2 (the server refuses the split from any day after the first; from the first day it is all events), and the server's 422 `series_refused` stays as the backstop. A date edited on its own that is moving to another calendar loses following through the same function. Every series dialog has Change scope: delete following and an answer from a day on return to the row that asked, and the choice made there goes through the same preview path. Verified 2026-11-05: the smoke section "the scopes an occurrence has, one rule for every chooser". Settled 2026-11-05.
- **An UNTIL after a drag.** Status: choice. Kept as the end by default, rewritten as the latest image at or before it, with "keep N events" offered when the count changes. Settled 2026-11-02.
- **How far an unbounded series is read.** Status: workaround, its rule decided. Chosen: one whole cycle of the rule's periods past the latest day the change names, widened by the change's reach (series model, Bounds), no number chosen. The code still reads a span by family, since listing every loss over a whole cycle proved too slow to build as a list (over 4 minutes for the model's tests, out of memory); it lands with losses and gains reported by class, a change to the plan's contract and the harness's window. Settled 2026-11-04.
- **No display cap.** Status: choice. Bounds and splits are worked out over the actual span; the one limit left (400,000 occurrences) is a refusal, never a partial result. Settled 2026-11-02.
- **Rules several times a day.** Status: choice. Every series-wide move of their days, time or zone is refused with its reason; "this event" edits a day by its key. Why: only imports carry them, and the identity machinery for two occurrences a day isn't worth building for them. Settled 2026-11-02.
- **An edited day's all-day flag.** Status: choice. A field like the others; a day deliberately timed in an all-day series stays timed when the series toggles. Reverses the first draft's decision 8. Settled 2026-11-02.
- **What an outcome is.** Status: choice. A day's outcome comes from its start instant and its kind before and after, never its dates; a day whose length alone changes "stays". Verified: the harness's placement check and its mutation. Settled 2026-11-04.
- **A skip belongs to the occurrence it removed.** Status: choice. It moves with that occurrence and is dropped with it, never carried onto a day the person never removed. Verified: the harness. Settled 2026-11-02.
- **The plan's zone.** Status: choice. The series' zone after the change, with every timed value of both sides written in it; an all-day series has no plan zone and its timed days are written in their own. Why: one zone to read a comparison in. Verified: the harness's placement checks. Settled 2026-11-04.
- **The zone "same moment" choice with a member reading.** Status: choice, for 1.5.1. Chosen: "same moment" keeps every row's own instant. The series repeats at the instant the day acted on keeps, read as a clock in the new zone; every edited day keeps the instant it shows at and lands on whatever local day that instant has in the new zone (a day with its own time may not change its date at all), a day on a date of its own at the series' time as much as one at its own time, its inherited time moved only on the clock it showed on (fixed 2026-11-05: its old-zone date was read at the new zone's clock, a day off; `server/tests/series-model.php`, "Zone moment, no drag: a day on its own date", and the database suite's "the same moment in another zone"); a skip stays on its occurrence; nothing is measured as a drag. Rejected: reading the change as a drag by the day shift the day acted on showed, so that every edited day moves a day later. Why: the shift was an artifact of subtracting a day read in the new zone from one read in the old, not a thing anyone asked for, and it is wrong for a day whose own clock doesn't cross midnight; the dialog already lists the occurrences whose instants differ where the two places change their clocks on different weeks. How it is built: the request's wall clock is read on the clock it showed on, any drag in it is measured in the old zone alone, and the result is carried to the new zone by the two zones' offsets at that instant: the series' clock there and the days its instants move on the new calendar, every member alike (the drag table's whole-pattern shift by those days). Verified 2026-11-04: `server/tests/series-model.php`, "Zone moment:" (the example above, both readings, and an edited day at its own time keeping its instant) and F9 (a gap day carries the series as any other). Where: [#202](https://github.com/Oshyan/better-cal/issues/202), [series model](series-model.md#zones-dst-and-all-day-days). Deferred 2026-11-04; decided 2026-11-04; built 2026-11-04.
- **A monthly or yearly carry across a day boundary.** Status: choice. Chosen: when the same moment carries a monthly or yearly series to another day on the new zone's calendar, the carry is the drag table's whole-pattern shift by those days and takes its preselected reading where the family offers several. Why: RFC 5545 defines a rule in one zone and says nothing of a rule carried to another, so the standard leaves it undefined; reading it as the drag the dialog would preselect keeps one rule for every shift. Verified: the harness's oracle takes the same reading (README, Known, Accepted Differences). Where: [series model](series-model.md#zones-dst-and-all-day-days). Settled 2026-11-05.
- **A rule the expander can't read.** Status: choice. Its COUNT or UNTIL is still read from the text, so the plan says how it ends, with no dates. Settled 2026-11-04.
- **"This and following" and deletes.** Status: choice, built for 1.5.1. A split is a bound change on the old series (UNTIL at its last occurrence before the day acted on, the skips and edited days keyed before it kept) plus the part from that day as a series of its own, planned as a whole series under the edit, previewed and committed through the plan API like any change, in one Undo entry; delete following is the old part alone, an answer from a day on the split with no fields and then the answer. Sent without a plan it is 409, since a split always changes a bound. Was: 1.5.0 kept their 1.4.6 code and the drop chip. Verified 2026-11-04: `server/tests/db/series-split.test.php` (preview, commit with each choice, stale and missing plans, delete following and an answer, each undone; a part's BYHOUR in step with its start; a part made all-day losing its clock parts; a part several times a day refused all-day), with the PHP and database suites. The harness's driver still sends these without a plan, so until its owner moves it onto the plan API its following cases fail as `series_plan_required` under its known cause. Settled 2026-11-02; built 2026-11-04.
- **A split's sent rule.** Status: choice, built for 1.5.1. Chosen: the rule sent with "this and following" is compared with the series' rule as shown, which is what the editor showed and sent back, never with the new part's, so the model's "A sent rule that is unchanged is no rule" holds for a split exactly as for the whole series, and the part keeps the rest of the series' count. A changed COUNT is the series' whole count, the part taking what is left of it (preselected, since the number shown was the series'), with that many from this day on as the other reading in the bound group (`whole`, `part`), each option showing its end; a whole count the old part already reaches leaves the part nothing and is disabled (`empty`). A changed UNTIL is the part's end as sent; one before the split day leaves the part nothing and is refused as an end before the start is, the same code and words (`empty`), nothing written. Was: the rule went to the part as sent and was compared with the part's own, so a COUNT=6 sent back unchanged gave the part six more events than the series showed, and an UNTIL before the series' last day, split there, read as the end it already had (found by the edit harness after "this and following" moved onto the plan API). Verified 2026-11-05: `server/tests/db/series-split.test.php`, "the series' rule sent back unchanged", "a changed count" and "a sent end before the split day", each committed or refused and undone. Where: [series model](series-model.md#changing-the-series-from-an-edited-day), api-contract "This and following". Settled 2026-11-05.
- **Google calendars.** Status: planned. Until 1.5.2, only edits that keep the rule's text are offered there, their effect on edited days unchecked, and a plan note says so. Nothing about Google's handling of exceptions is claimed verified before the probe reads back what it stored. Settled 2026-11-02.
- **Floating times.** Status: planned. The plan is data, and the app composes its sentences in the person's locale and time format.

## Trips and Links

- **A trip never contains a trip.** Status: choice. One end-state rule checked after every write, by the writers and by Undo alike; Undo refuses a state that would break it and says what it would break. Else: one-direction guards at each writer, which 1.5.0's first candidate had and which let a nesting through a dormant link. Verified: the database suite's trip tests and the two Undo-gate mutations. Verified 2026-11-05 that no undo goes around the gate ([#202](https://github.com/Oshyan/better-cal/issues/202), "Undo passes the trip gate"): the last change, an entry by id with and without force, a run strict and not, and a proposal's undo all restore through one path that ends in `Trips::assertRules`, and a plugin's write-back undo restores only an event's time; `server/tests/db/undo-trips.test.php` runs each case through every one of those paths, the issue's example among them ("detach, then flag the stop"). Settled 2026-11-04.
- **A link whose flags are both clear stays.** Status: choice. It is a relationship the person made and stands until they remove it; the end-state rule alone judges it. It stays visible and removable in the editor. Settled 2026-11-04.
- **A row exists for its own fields and for whatever refers to it.** Status: choice, built for 1.5.1. ## Request Credentials

- **What a request may write, and when its credential is checked.** Status: choice. A write made under a request is one of two things. Either it is a change to what the account holds, made inside a transaction in which the request's session, API key or proved password was checked with a lock: `Undo::write` where the change is journaled, `RequestAuthority::checkedTx` where it is not. Or it is bookkeeping the server keeps about requests themselves, which belongs to no account and is written the same whoever asked. The bookkeeping is a fixed list of tables, `RequestAuthority::BOOKKEEPING`, each with its reason: throttle counters (`rate_events`), admission to the model and to outside actions (`model_admissions`, `external_action_admissions`), lookup caches (`http_cache`, `geocode_cache`) and the server's health record (`system_health`). Nothing else is on it. A write to any other table outside a checked transaction is a journaling misuse: logged in production, failing the suites. Why: a credential revoked after a request signed in then stops every change the request has not yet committed, whichever route it came by, and a new route can't forget the check. A flow that ends its own credential (signing out, a key revoking itself, a password change) checks it and ends it in one transaction and writes nothing after; a password change signs in again and writes the rest as the new session. The account's change marker moves in the checked transaction of a request that may change things, not after the response. A request's work run after its response (a plugin's queued job) runs under the same credential. Verified 2026-11-05: the write-boundary checks in the PHP suite, `server/tests/db/revocation.test.php`, and the completeness test run with every request operation's credential registered. Where: `server/src/Domain/RequestAuthority.php`. Settled 2026-11-05 for 1.5.1.
- **An undo and its CalDAV journal are one transaction.** Status: choice. The undo's restore, its mark as undone and the `dav_changes` rows that tell CalDAV clients are written in the one transaction that checked the request's credential, the rule above applied to the journal: check and write together. Else: the journal in a checked transaction of its own after the restore commits, which 1.5.1's first candidate had, where a credential revoked between the two left the undo done, the request failing and CalDAV clients never told. Verified 2026-11-05: `server/tests/db/undo.test.php` revokes the credential the moment another connection sees the undo committed, and the undo still answers ok with its journal row written. Where: `Undo::apply`. Settled 2026-11-05 for 1.5.1.
- **A job queue's state is the server's own record.** Status: choice. A request's work run after its response (a plugin's queued job) runs under the request's credential and is checked at its writes; whether the queue claimed it, finished it or failed it is the server's, written as no request (`RequestAuthority::asServer`). The `jobs` table is not on the bookkeeping list, because a job row is queued by a request, under its check; only its claim, done and failed marks are written apart. A credential revoked meanwhile fails the job once, for good: nothing is left running until stall recovery, and the worker never reruns it with no credential. Verified 2026-11-05: `server/tests/db/revocation.test.php` revokes a session and an API key during a run. Where: `Plugins::runQueuedNow`, `JobQueue::markFailed`. Settled 2026-11-05 for 1.5.1.
- **The address cache stays bookkeeping.** Status: choice. `geocode_cache` is keyed by the location text someone typed, and stays on the list: its row is the same whoever asks (a text and where it is), it belongs to no account and nothing reads it but the same lookup, so a revoked request can at most add an address string to a shared cache. `http_cache`, keyed by a URL, is the same shape. Settled 2026-11-05 for 1.5.1.

## Revisiting One

Changing a choice is a changed decision: change the rule where it lives, say so in the changelog, and update the entry with the new reading and the date, keeping the old one as "was". Repairing code that broke a recorded choice is a bug fix, and the entry's verification line is what changes. A defect's entry is closed when its repair lands, with the release named.
