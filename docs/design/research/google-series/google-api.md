# Google Calendar API: recurring events, what the docs say

All pages read 2026-11-07. Each source's own "Last updated" stamp is listed at the end. Quotes are verbatim; everything else is a close paraphrase of the cited page.

## Summary

- `recurrence` takes RRULE, EXRULE, RDATE and EXDATE lines; DTSTART and DTEND are forbidden there. The reference lists EXRULE; the concepts guide lists only RRULE, RDATE, EXDATE.
- For a recurring master, `start.timeZone` / `end.timeZone` are required and are the zone the rule expands in. All-day series use dates in EXDATE/RDATE and a date UNTIL in the only example.
- Google documents no RRULE normalisation, no part limits and no rejected forms. The 730-occurrence cap appears only in the end-user Help Center. An official page does use `BYMONTHDAY=-1` (the Feb 29 birthday rule).
- Instances are identified by `recurringEventId` + `originalStartTime` (immutable). Cancelled exceptions carry only `id`, `recurringEventId` and `originalStartTime` for sure, and clients must keep them for the life of the parent.
- The "this and following" recipe (trim the old series with UNTIL or COUNT, insert a new one) and its note that the split "resets any exceptions happening after the target instance" were **removed** from the guide between the 2026-05-26 and 2026-09-17 versions. Today the guide only warns against doing it instance by instance.
- Nothing current says what happens to existing exceptions when the master's rule or start changes. A 2011 Google blog post says exceptions are "preserved even if the recurring event itself is updated."
- Change detection: per-event `etag` with `If-Match` (412 on mismatch) and `If-None-Match` (304); `syncToken` on `events.list` only, 410 means wipe and full resync. `events.watch` pushes a body-less "something changed" ping on channels that expire (default TTL 7 days) and never renew themselves.
- `sendUpdates` takes `all`, `externalOnly` or `none`. The docs never give a clear default for patch, update or delete. Nothing documents how instance patches affect attendees or mail.
- A client-chosen `id` is base32hex (`a-v`, `0-9`), 5 to 1024 chars, unique per calendar. Use `import` with `iCalUID` to bring in a private copy without mailing anyone. Patch costs 3 quota units.

## 1. The `recurrence` field

**Accepted lines**
- Reference: "List of RRULE, EXRULE, RDATE and EXDATE lines for a recurring event, as specified in RFC5545. Note that DTSTART and DTEND lines are not allowed in this field; event start and end times are specified in the start and end fields. This field is omitted for single events or instances of recurring events." (https://developers.google.com/workspace/calendar/api/v3/reference/events)
- The concepts guide names only three: "The recurrence field contains an array of strings representing one or several RRULE, RDATE or EXDATE properties as defined in RFC 5545." EXRULE never appears there. (https://developers.google.com/workspace/calendar/api/concepts/events-calendars) This is a conflict between two pages, and EXRULE is deprecated in RFC 5545 itself.
- "Each of the properties may occur within the recurrence field multiple times. The recurrence is defined as the union of all RRULE and RDATE rules, minus the ones excluded by all EXDATE rules." (concepts) EXRULE is left out of that definition.
- The series is defined in two parts: the start and end fields, which "define the first occurrence, as if this were just a stand-alone single event", and the recurrence field. (concepts) Reference: `start` is "The (inclusive) start time of the event. For a recurring event, this is the start time of the first instance." `end` is "(exclusive)", and for a recurring event it is "the end time of the first instance." (reference)
- The RRULE parts the guide names are FREQ ("Required"), INTERVAL, COUNT, UNTIL ("The date or date-time until which the event should be repeated (inclusive)") and BYDAY, plus "Other similar components include BYMONTH, BYYEARDAY, and BYHOUR." (concepts) BYSETPOS, BYMONTHDAY, BYWEEKNO, WKST, BYMINUTE and BYSECOND go unmentioned.
- "You can use either COUNT or UNTIL to specify the end of the event recurrence. Don't use both in the same rule." (concepts)
- EXDATE "must point to a valid instance generated by the recurrence rule." (concepts) The page doesn't say what Google does with an EXDATE that matches no instance (rejects it, drops it, or keeps it silently).
- "EXDATE and RDATE can have a time zone, and must be dates (not date-times) for all-day events." (concepts)

**UNTIL, timed vs all-day**
- Timed example: `"RRULE:FREQ=WEEKLY;UNTIL=20110701T170000Z"` on a master starting `2011-06-03T10:00:00.000-07:00` with `timeZone: America/Los_Angeles`. That UNTIL is UTC, and it equals the 10:00 local start of the last wanted instance. (https://developers.google.com/workspace/calendar/api/guides/recurringevents)
- All-day example: `"RRULE:FREQ=DAILY;UNTIL=20150628;INTERVAL=3"` with `"EXDATE;VALUE=DATE:20150610"` and `"RDATE;VALUE=DATE:20150609,20150611"` on `start.date 2015-06-01`. (concepts)
- Google states no rule for UNTIL's form. The examples follow RFC 5545 3.3.10, which says UNTIL must match DTSTART's value type, and must be UTC when DTSTART is a local time with a time zone (https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10). The docs never say whether Google accepts, rewrites or rejects a floating UNTIL, a TZID-local UNTIL, or a date-time UNTIL on an all-day series.

**Time zone of the master**
- `start.timeZone`: "For recurring events this field is required and specifies the time zone in which the recurrence is expanded. For single events this field is optional and indicates a custom time zone for the event start/end." `end.timeZone` has identical text. (reference)
- "For recurring events, you must always specify a single time zone to expand the recurrences of the event." (concepts) The docs don't say whether start and end may carry different zones on a recurring event, or what happens if they do.
- 2011 Google blog: "a timezone identifier for both the start and end time is always required for recurring events, so that expansion happens correctly if part of a series occurs during daylight savings time." (https://gsuite-developers.googleblog.com/2011/12/calendar-v3-best-practices-recurring.html)
- "Note that the timezone field has no significance for all-day events." (concepts)
- Responses come back in the `timeZone` request parameter if one is given, otherwise in the calendar's zone. The calendar zone also decides whether an all-day event falls inside a `timeMin`/`timeMax` window. (concepts)

**Normalisation and limits: undocumented**
- No current developers.google.com page says whether Google rewrites a rule when reading it back. That covers reordering parts, dropping WKST, converting COUNT to UNTIL, changing BYDAY or BYMONTHDAY forms, folding RDATE/EXDATE lines, or changing UNTIL precision.
- No page lists rejected or unsupported RRULE parts. `BYSETPOS` and `BYMONTHDAY=28,29,30;BYSETPOS=-1` are never mentioned.
- `BYMONTHDAY=-1` does appear in an official doc. Birthday events "falling on 29th of February must have the following recurrence rule: 'RRULE:FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=-1'." (https://developers.google.com/workspace/calendar/api/guides/event-types) That shows the backend accepts at least that negative BYMONTHDAY form for that event type. It doesn't prove it for `default` events.
- The only published occurrence cap is in the end-user Help Center: "Repeating events in Google Calendar have a limit of 730 occurrences." (https://support.google.com/calendar/answer/37115) The API docs never say whether the API enforces this, truncates expansion at 730, or rejects longer rules.
- The CalDAV guide says data "is formatted according to the iCalendar specification" and lists unsupported features (VTODO, VJOURNAL, AUDIO and others). It says nothing about RRULE parts. (https://developers.google.com/workspace/calendar/caldav/v2/guide)

**Other recurring-specific constraints**
- `eventType` "cannot be modified after the event is created." Birthday events must use `RRULE:FREQ=YEARLY` and allow only a few properties. (reference; event-types guide)
- Visibility on instances: "If the new setting is more restrictive (e.g. from public to private), it is applied to all instances. If the new setting is less restrictive (e.g. from private to public), the change is ignored. To make a recurring event less restrictive, you must update the parent recurring event." (reference; also release notes, 2026-07-07 entry, https://developers.google.com/workspace/calendar/release-notes)
- `locked`: on a locked event copy, "no changes can be made to the main event fields "summary", "description", "location", "start", "end" or "recurrence"." (reference)

## 2. `events.instances` vs `events.list` with `singleEvents`

**What each returns**
- `events.instances`: "Returns instances of the specified recurring event." `GET .../calendars/calendarId/events/eventId/instances`, where `eventId` is the "Recurring event identifier." (https://developers.google.com/workspace/calendar/api/v3/reference/events/instances)
- `events.list` default: "by default only returns single events, recurring events, and exceptions; instances that are not exceptions are not returned." With `singleEvents=true`, "all individual instances appear in the result, but underlying recurring events don't." Free/busy readers always get the `singleEvents=true` behavior. (guide)
- `singleEvents`: "Whether to expand recurring events into instances and only return single one-off events and instances of recurring events, but not the underlying recurring events themselves. Optional. The default is False." (https://developers.google.com/workspace/calendar/api/v3/reference/events/list)
- `orderBy=startTime` "is only available when querying single events (i.e. the parameter singleEvents is True)." Without it the order is "an unspecified, stable order." (list)
- "Unlike their parent recurring events, instances do not have the recurrence field set." (guide)

**Instance identity**
- `recurringEventId`: "For an instance of a recurring event, this is the id of the recurring event to which this instance belongs. Immutable." (reference)
- `originalStartTime`: "the time at which this event would start according to the recurrence data in the recurring event identified by recurringEventId. It uniquely identifies the instance within the recurring event series even if the instance was moved to a different time. Immutable." It has `date`, `dateTime` and `timeZone` subfields, the same shape as `start`. (reference)
- `instances` takes `originalStart`, "The original start time of the instance in the result." (instances) The 2011 blog says a query with `originalStart` "would return a collection with either zero or one item, depending on whether the instance with the exact original start date exists." (blog)
- Instance ids: the reference says only that "in recurring events, all occurrences of one event have different ids while they all share the same iCalUIDs." (reference) The 2011 blog shows the instance id `7n6f7a9g8a483r95t8en23rfs4_20111212T090000Z`, which is the parent id, an underscore, and the original start in UTC basic format. No current page documents this format. The all-day form is undocumented.

**Paging and windows**
- Both methods: `maxResults` defaults to 250, and "The page size can never be larger than 2500 events." (instances; list)
- `list` warns that "The number of events in the resulting page may be less than this value, or none at all, even if there are more events matching the query. Incomplete pages can be detected by a non-empty nextPageToken field in the response." (list)
- The `timeMin` wording differs between the two pages. `list` says "Lower bound (exclusive) for an event's end time to filter by", while `instances` says "Lower bound (inclusive) for an event's end time to filter by." Both say `timeMax` is "Upper bound (exclusive) for an event's start time." Both need an RFC 3339 offset. (list; instances)
- The `instances` response schema includes `nextSyncToken` ("Omitted if further results are available"), yet the method takes no `syncToken` parameter. (instances)

**Cancelled instances, `showDeleted`, `syncToken`**
- `status` "cancelled": "Cancelled exceptions of an uncancelled recurring event indicate that this instance should no longer be presented to the user. Clients should store these events for the lifetime of the parent recurring event. Cancelled exceptions are only guaranteed to have values for the id, recurringEventId and originalStartTime fields populated. The other fields might be empty." (reference)
- For all other cancelled events: "Clients should remove their locally synced copies. Such cancelled events will eventually disappear, so do not rely on them being available indefinitely. Deleted events are only guaranteed to have the id field populated." On the organizer's calendar, cancelled events keep their details so they can be undeleted, "However, incremental sync requests with showDeleted set to false will not return these details." (reference)
- "The list method returns cancelled events only on incremental sync (when syncToken or updatedMin are specified) or if the showDeleted flag is set to true. The get method always returns them." (reference)
- `list` `showDeleted`: "Cancelled instances of recurring events (but not the underlying recurring event) will still be included if showDeleted and singleEvents are both False. If showDeleted and singleEvents are both True, only single instances of deleted events (but not the underlying recurring events) are returned. Optional. The default is False." (list) So a plain list without `singleEvents` already returns cancelled exceptions. With `singleEvents=true` and `showDeleted=false`, skipped occurrences just vanish.
- `instances` `showDeleted`: "Cancelled instances of recurring events will still be included if singleEvents is False. Optional. The default is False." (instances) The instances method has no `singleEvents` parameter, so this sentence is ambiguous for that endpoint.
- `list` `syncToken`: "All events deleted since the previous list request will always be in the result set and it is not allowed to set showDeleted to False." It can't be combined with `iCalUID`, `orderBy`, `privateExtendedProperty`, `q`, `sharedExtendedProperty`, `timeMin`, `timeMax` or `updatedMin`. "All other query parameters should be the same as for the initial synchronization to avoid undefined behavior." (list) The sync guide's own example pairs `singleEvents=true` with `syncToken`. (https://developers.google.com/workspace/calendar/api/guides/sync)
- `updatedMin`: "When specified, entries deleted since this time will always be included regardless of showDeleted." (list)

## 3. Exceptions: how each kind is made and read back

**Moved or field-changed occurrence**
- "To modify a single instance (creating an exception), client applications must first retrieve the instance and then update it by sending an authorized PUT request to the instance edit URL", that is `.../calendars/calendarId/events/instanceId`. Success returns 200 "with the updated instance." (guide) The guide shows only PUT (update). It never shows patch on an instance, though nothing forbids it.
- "Instances that differ from their parent recurring event are called exceptions. For example, an exception may have a different summary, a different start time, or additional attendees invited only to that instance." (concepts)
- A moved exception keeps its `originalStartTime`. The blog says "The original start date in the event is kept, and serves as an identifier of the instance within the series." (blog; reference)

**Skipped occurrence**
- The documented method is updating the instance with `"status": "cancelled"` (PUT). The guide's example response is a full event, with `recurringEventId`, `originalStartTime` and the other fields. (guide)
- Calling `events.delete` on an instance id isn't documented for this purpose. The delete page says only "Deletes an event." (https://developers.google.com/workspace/calendar/api/v3/reference/events/delete) Errors guide: 410 "can also occur if a request attempts to delete an event that has already been deleted." (https://developers.google.com/workspace/calendar/api/guides/errors)
- The docs don't say whether a cancelled instance shows up as an EXDATE in the master's `recurrence`, or only as a separate cancelled exception record.

**"This and following" (split)**
- Current guide (2026-09-17) has only the warning: "Do not modify instances individually when you want to modify the entire recurring event, or "this and following" instances. This creates lots of exceptions that clutter the calendar, slowing down access and sending a high number of change notifications to users." (guide)
- Earlier versions, up to at least the 2026-05-26 version, had a section titled "Modify all following instances". The archived copy (https://web.archive.org/web/20260802102559/https://developers.google.com/workspace/calendar/api/guides/recurringevents) said to make "two separate API requests":
  - "Call events.update() to trim the original recurring event of the instances to be updated. Do this by setting the UNTIL component of the RRULE to point before the start time of the first target instance. Alternatively, you can set the COUNT component instead of UNTIL."
  - "Call events.insert() to create a new recurring event with all the same data as the original, except for the change you are attempting to make. The new recurring event must have the start time of the target instance."
  - Its example trimmed a weekly 10:00 America/Los_Angeles series to `UNTIL=20110617T065959Z`, with the target instance at 2011-06-17 10:00 local. That UNTIL is one second before local midnight that day, not just before the target's start. The new series used `RRULE:FREQ=WEEKLY`. (The 2023 copy wrongly gave the new event the same UNTIL; https://web.archive.org/web/20231026110934/https://developers.google.com/calendar/api/guides/recurringevents)
  - "Note: Changing all following instances resets any exceptions happening after the target instance."
- That section, and the "resets any exceptions" note, are gone from the live page. No replacement says how Google now wants a split done, or what happens to exceptions after the split point.
- No doc says whether the new series is linked to the old one (shared `iCalUID`, a RELATED-TO, or anything else). It's implied that it gets a fresh `id`. The docs are silent on `iCalUID`.

**Changing the whole series' rule or start**
- No current developers.google.com page covers it. The 2011 blog says exceptions "are still part of the series, but changes are preserved even if the recurring event itself is updated." (blog) It doesn't separate field changes from rule or start changes.
- The same blog's editor's note (2012-02-20) says Google removed "references to API call which reverted changes made to an individual instance. This feature was deprecated." So there is no documented "reset this instance to the series" call. (blog)
- The docs say nothing about what happens to exceptions (moved, cancelled or edited) whose `originalStartTime` no longer falls on the new rule, or whether they get re-keyed when the master's start time moves.

## 4. Change detection

- `etag`: "ETag of the resource." (reference) "Every resource has a version field that changes every time the resource changes" (the etag). (https://developers.google.com/workspace/calendar/api/guides/version-resources)
- `If-Match` on update or delete: if the etag hasn't changed, "the modification succeeds and the new version of the resource with the new etag is returned. Otherwise, you will get a 412 (Precondition failed) response code." (version guide) 412 has reason `conditionNotMet`. (errors)
- "There is no support for conditional modifications for insert operations. Instead, it is guaranteed that if you are allowed to provide a resource ID, then the operation will only succeed if no existing entry has that ID." (version guide) A duplicate id gives `409` with reason `duplicate`, "The requested identifier already exists." (errors)
- `If-None-Match` on get returns `304` when unchanged. The guide notes "There are special cases in which etags won't change, such as when one of the read-only fields of a calendarList entry changes". (version guide)
- The `update` page: "To do a partial update, perform a get followed by an update using etags to ensure atomicity." (https://developers.google.com/workspace/calendar/api/v3/reference/events/update) The generic performance guide mentions `If-Match: *` to force a patch through. (https://developers.google.com/workspace/calendar/api/guides/performance)
- The docs don't say whether editing an instance changes the parent master's etag, or the reverse.
- `updated`: "Last modification time of the main event data (as a RFC3339 timestamp). Updating event reminders will not cause this to change. Read-only." (reference)
- `sequence`: "Sequence number as per iCalendar." Writable. (reference) The docs don't say when Google bumps it.
- `syncToken` lifecycle: `nextSyncToken` arrives only on the last page. Paging during sync is safe ("they won't be missed"). A large incremental sync may return a `pageToken` instead, and you then repeat "the exact same list query ... (with the exact same syncToken)". Disallowed parameters return 400. "Sometimes sync tokens are invalidated by the server, for various reasons including token expiration or changes in related ACLs. In such cases, the server will respond to an incremental request with a response code 410. This should trigger a full wipe of the client's store and a new full sync." (sync guide) The 410 reasons are `fullSyncRequired` and `updatedMinTooLongAgo`. (errors) No token lifetime is documented.
- Legacy `updatedMin` sync "is no longer recommended as it is more error-prone with respect to missed updates". (sync guide)
- `events.watch`: the body takes `id`, `token`, `type` (`web_hook`), `address` and `params.ttl`. "The time-to-live in seconds for the notification channel. Default is 604800 seconds." It can filter by `eventTypes`. (https://developers.google.com/workspace/calendar/api/v3/reference/events/watch)
- Push guide: a channel id has a "Maximum length: 64 characters". The token is 256 characters. The address must be HTTPS with a valid certificate. The first message has `X-Goog-Resource-State: sync` and message number 1. Later ones are `exists`. Message numbers increase "though the message numbers will not be sequential." "Notification messages posted by the Google Calendar API to your receiving URL do not include a message body. These messages do not contain specific information about updated resources". "Currently, there's no automatic way to renew a notification channel." Respond with 200, 201, 202, 204 or 102. Google retries 500, 502, 503 and 504 with backoff. (https://developers.google.com/workspace/calendar/api/guides/push) There's no delivery guarantee or latency figure.

## 5. Invitations and notifications

- `sendUpdates` on insert, update, patch, delete and move: `"all"`, `"externalOnly"` ("Notifications are sent to non-Google Calendar guests only.") and `"none"`. For calendar migration tasks, "consider using the Events.import method instead." (patch; update; delete; move pages)
- Defaults: the insert page says of `sendUpdates`, "Note that some emails might still be sent. The default is false." That's odd wording for a string parameter. Patch, update and delete give a default only for the deprecated `sendNotifications` ("The default is false"), and say "some emails might still be sent even if you set the value to false." None states a `sendUpdates` default. (https://developers.google.com/workspace/calendar/api/v3/reference/events/insert; patch; update; delete)
- Insert warns about `none`: it "can have significant adverse effects, including events not syncing to external calendars or events being lost altogether for some users." (insert)
- Create guide: "If you set sendUpdates to "all" or "externalOnly" in your insert request, the corresponding attendees receive an email notification for your event." (https://developers.google.com/workspace/calendar/api/guides/create-events)
- Propagation: the organizer calendar "owns the shared event information, including ID, start and end time, summary, and description. When this information is updated on the organizer calendar, the changes are propagated to attendee copies." Reminders, colorId, transparency and private extended properties are per copy. "The only event change that is propagated from attendees back to the organizer is the attendee's response status". (https://developers.google.com/workspace/calendar/api/concepts/inviting-attendees-to-events)
- Setting a shared property on a non-organizer copy gives 403 `forbiddenForNonOrganizer`. (errors)
- Import adds an event "directly in the attendee's calendar" with "the same event ID (iCalUID)", and "the attendee can see the event in their calendar, but doesn't receive an invitation email from Calendar." (inviting guide)
- More than 200 guests: "response status is not propagated to the guests." (reference; inviting guide)
- Per-instance attendee changes are allowed: an exception may have "additional attendees invited only to that instance." (concepts) Editing instances one by one sends "a high number of change notifications to users." (guide)
- The docs never say what an instance patch with `sendUpdates=all` mails out (one instance or the whole series), whether a patch to an instance that leaves `attendees` out keeps the series attendees, or how a series-wide attendee change merges with per-instance attendee lists.
- Workspace abuse limits: around 10,000 external invites in a short span, around 2,000 "email guests" emails to external guests, and more than 100,000 events created in a brief window all trigger throttling. (https://knowledge.workspace.google.com/admin/calendar/avoid-calendar-use-limits)

## 6. Ids, import vs insert, quotas

- `id` rules: "characters allowed in the ID are those used in base32hex encoding, i.e. lowercase letters a-v and digits 0-9, see section 3.1.2 in RFC2938", "the length of the ID must be between 5 and 1024 characters", "the ID must be unique per calendar". "Due to the globally distributed nature of the system, we cannot guarantee that ID collisions will be detected at event creation time." Google recommends an RFC 4122 UUID. Hex digits fall inside a-v, so a hex UUID with the dashes removed fits. (reference)
- `iCalUID`: "Event unique identifier as defined in RFC5545 ... must be supplied when importing events via the import method. Note that the iCalUID and the id are not identical and only one of them should be supplied at event creation time." Look one up with `events.list?iCalUID=`. (reference)
- `import`: "This operation is used to add a private copy of an existing event to a calendar. Only events with an eventType of default may be imported." Its required properties are `start`, `end` and `iCalUID`. `organizer` is "Read-only, except when importing an event." Import has no `sendUpdates` parameter. (https://developers.google.com/workspace/calendar/api/v3/reference/events/import)
- `originalStartTime` is marked writable in the insert, import and update request bodies. No doc explains importing an exception record on its own, or matching it to a master by `iCalUID` + `originalStartTime`. (insert; import; update)
- `move` changes the organizer. Only `default` events can be moved. (https://developers.google.com/workspace/calendar/api/v3/reference/events/move)
- Quotas for projects created on or after 2026-05-01: 10,000 requests per minute per project and 600 per minute per user per project, both on a sliding window, with a daily billing threshold of 1,000,000 requests per project. Rate-limit errors come back as 403 `userRateLimitExceeded`, 403/429 `rateLimitExceeded` or 403 `quotaExceeded`. Use truncated exponential backoff. (https://developers.google.com/workspace/calendar/api/guides/quota; errors)
- "Each patch request consumes three quota units; prefer using a get followed by an update." Patch replaces whole arrays: "Array fields, if specified, overwrite the existing arrays". (https://developers.google.com/workspace/calendar/api/v3/reference/events/patch)
- Batch: at most 1000 calls; each counts as one request; "The server might perform your calls in any order." So a split (trim + insert) can't count on order inside one batch. (https://developers.google.com/workspace/calendar/api/guides/batch)

## Open questions a probe must answer

1. Does insert accept EXRULE, and is it kept on read-back? Concepts and reference disagree.
2. Read-back normalisation: does Google reorder RRULE parts, drop or add WKST, rewrite COUNT as UNTIL, change UNTIL precision or form, or merge or split RDATE/EXDATE lines?
3. Which forms are rejected and which are accepted on `default` events: `BYMONTHDAY=-1`, `BYMONTHDAY=28,29,30;BYSETPOS=-1`, `BYDAY=-1FR`, `BYSETPOS` with BYDAY, BYWEEKNO, BYYEARDAY, FREQ=HOURLY/MINUTELY/SECONDLY, BYHOUR/BYMINUTE? What error comes back?
4. UNTIL forms: floating local, UTC, TZID-local, and a date-time on an all-day series. Which are accepted, and how are they stored?
5. Is the 730-occurrence cap enforced through the API (rejected, truncated, or expansion stops)? What happens with an unbounded rule under `singleEvents=true` + `syncToken`, which allows no `timeMax`?
6. Cancelling an instance with PUT `status: cancelled` vs `events.delete` on the instance id: same result? Does either add an EXDATE to the master's `recurrence`?
7. Patch (not PUT) on an instance: allowed? Is the instance id always `<parentId>_<UTC basic>` for timed and `<parentId>_<YYYYMMDD>` for all-day? Can you patch an instance id that was never listed?
8. Changing the master's start time (same rule): are exceptions kept, dropped, or re-keyed to the new `originalStartTime`? The same question for a changed RRULE (for example, weekday changed) and for a changed `start.timeZone`.
9. After a split (trim UNTIL + insert new): what happens to exceptions after the cut? The removed doc said "resets". Does the old master still own them as cancelled records? Does the new series share an `iCalUID`?
10. Does trimming with COUNT behave the same as UNTIL?
11. Does an instance edit change the master's `etag` or `updated`, and does a master edit change unmodified instances' etags? When is `sequence` bumped?
12. In `events.instances`, does `showDeleted=false` hide cancelled instances? What does its `nextSyncToken` mean, and can it be used? Is `timeMin` inclusive or exclusive on each endpoint?
13. Does a syncToken incremental list with `singleEvents=false` deliver a new or changed exception as its own record, and a master rule change as the master only?
14. `sendUpdates` default on patch, update and delete, observed by checking a test guest mailbox. What does an instance patch with `all` mail out? Does a patch to an instance that omits `attendees` keep the series list?
15. Does `import` with an exception record (`recurringEventId` or `originalStartTime` + same `iCalUID`) attach it to an imported master?
