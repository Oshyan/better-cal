# Better-Cal API Contract (v1)

Base path `/api/v1`. JSON everywhere. Auth: `bc_session` cookie; non-GET requires `X-CSRF` header. Alternative: `Authorization: Bearer bc_...` personal access token (CSRF-exempt; see Tokens). Errors: `{"error":{"code","message"}}`.

## Auth
- `POST /auth/login` `{email, password}` → `{ok:true}` + sets cookie. 401 `invalid_credentials` on failure (the same answer, in the same time, whether or not the account exists). 429 `too_many_attempts` with a `Retry-After` header and `error.retryAfter` seconds when this network address has sent too many wrong passwords: by default 10 in 15 minutes (`BETTERCAL_LOGIN_MAX_FAILURES`), counted together with CalDAV Basic-auth failures, which answer 429 the same way. The account is never locked. When failures from all addresses pass 60 in 15 minutes (from 10 or more addresses), addresses that have not signed in successfully in the last 30 days are refused until it subsides; known ones are not, and neither is a browser presenting a valid `bc_device` cookie (the refusal message then says new devices are paused). A successful sign-in also sets `bc_device`: a random device cookie (sha256-hashed in `trusted_devices`, one year, `Path=/api/v1/auth`, httpOnly, SameSite=Strict), replaced on each sign-in and kept on sign-out. It never authenticates anything by itself; it only exempts from that overall brake, and stops doing so after 3 wrong passwords sent with it in 15 minutes. A password reset forgets them all. A blocked attempt is refused before the password is looked at. The client address is the connecting peer unless `BETTERCAL_TRUSTED_PROXIES` lists it (then the rightmost untrusted `X-Forwarded-For` entry); IPv6 sources count per /64.
- `POST /auth/logout` `{pushEndpointHash?}` → `{ok:true}`. `pushEndpointHash` is this browser's SHA-256 endpoint identity; when present, logout atomically removes only that server-side reminder device with the session. The browser subscription stays intact so signing in again can restore reminders without another permission prompt.
- `POST /auth/step-up` `{password}` → `{ok:true}`: confirms the current session for sensitive Google actions for 10 minutes. Session + CSRF required; 403 `invalid_credentials`, 403 `session_required`, or the shared 429 `too_many_attempts` response. A fresh password login already counts as confirmed. An endpoint that needs this confirmation answers 403 `step_up_required` without it.
- `GET /auth/sessions` → `{others}`: how many other browsers are signed in. Session only.
- `POST /auth/sign-out-others` `{keepPushHash?}` → `{sessions, devices, pushDevices, feedsRotated, notifyEmailReset}`: signs out every other browser session, forgets every other remembered browser (`bc_device`), removes every push device except the one whose endpoint sha256 is `keepPushHash`, rotates every session-created/legacy public feed URL, and returns a session-set custom reminder address to the account email. The calling browser stays signed in. API tokens and token-created channels are untouched. Written to Activity. Session only: an API token gets 403 `session_required`.
- `GET /me` → `{user:{id,email,displayName,settings}, csrf}` or 401. (`csrf` is null under bearer auth.) `settings` is the same merged object returned by `GET /settings` (stored values over defaults).

## Personal access tokens
Token value: `bc_` + 43 url-safe base64 chars; stored sha256-hashed, shown once at creation. Bearer requests skip CSRF. Management endpoints are session-auth only: a bearer token gets 403 `session_required`. Creating a token in the browser also requires password authentication within the last ten minutes.
- `GET /tokens` → `{tokens:[{id,name,createdAt,lastUsedAt}]}`.
- `POST /tokens` `{name}` (at most 120 characters) → `{id,name,token}` (201; token shown once).
- `DELETE /tokens/:id` → `{ok:true,subscriptionsPaused}`. Token-created ICS subscriptions pause but retain their cached calendar data for owner review.
- CLI equivalent: `php server/bin/token.php --create --name=X | --list | --revoke=ID`. In the app: Settings, Account, API keys (create shows the value once; revoke is immediate).
- Agent-facing guide: [agent-api.md](agent-api.md); MCP server in `tools/mcp/`.

## Calendars & structure
- `GET /calendars` → `{calendars:[{id,name,color,kind,role,provider,sourceUrl,googleCalendarId,googleAccessRole,editable:boolean,pluginId,pluginSettings,visible,position,pollIntervalMinutes,staleAfterDays,folderIds:[],tagNames:[],groupSimilar:boolean,reminderDefaults:object|null,subscriptionAuthorization:{status:"active"|"paused",origin:"owner"|"token"|"legacy_review",reason:string|null}|null,health:{lastPolledAt,status,error,content,eventCount,stale:boolean}}], folders:[{id,name,position}], tags:[{id,name}]}` `role` is what the calendar is to the person: `mine` (events are planned unless tentative), `opportunities` (events are available until picked), `context` (information: never planned, never busy, drawn quietly). Defaults: local → mine, subscribed → opportunities, plugin → context; `PATCH /calendars/:id {role}` changes it. `provider` is `ics` (an address we fetch; `sourceUrl` set for a browser session) or `google` (through a connected Google account; `googleCalendarId` and `googleAccessRole` set, `sourceUrl` null). A bearer token receives an ICS `sourceUrl` only for a subscription that exact token created; other stored source capabilities are returned as null. The same rule applies to calendar mutation responses. Both providers are `kind=subscribed`. `editable` says whether events on the calendar can be created, edited and deleted here: true for local calendars and for Google calendars whose role is `writer` or `owner` (write-through to Google, see `docs/google-calendar.md`); false for feeds, view-only Google calendars and plugin calendars. Clients gate editing on `editable`, not on `kind`. Feed `health` separates three independent questions. `status` (`ok|error|never`) + `error`: did the last fetch work. `content`: what the last *successful* fetch looked like — `active` (has events, or changed recently), `empty` (no events, and never had any: a fresh or quiet feed, not a problem), `emptied` (no events now but had some on an earlier poll: how expired tokens and broken sources fail, since they keep returning a valid empty calendar), `stale` (unchanged for `staleAfterDays` since it was last seen to change or since subscription, AND nothing upcoming). `eventCount` is the last successful poll's VEVENT count. `stale` is `content === "stale"` and no longer folds in `status === "error"`. For local calendars `content` is `active` and the rest is null/`never`.
- `POST /calendars` `{name,color,role?,folderIds?,tagNames?}` → calendar object (201).
- `PATCH /calendars/:id` (any of name,color,visible,position,role,folderIds,tagNames,pollIntervalMinutes,staleAfterDays,groupSimilar,reminderDefaults) → calendar object. `pollIntervalMinutes` is at least 5, `staleAfterDays` at least 1.
- `reminderDefaults` (per calendar, persisted in `calendars.settings_json`): `{timed:[{minutes:int}], allDay:[{daysBefore:int, time:"HH:MM"}]}` or `null` to clear (fall through to the global defaults in Settings). A missing key inside the object means "none" for that event type. See Reminders below for how defaults resolve.
- `groupSimilar` (boolean, per calendar, persisted in `calendars.settings_json`): whether the client should visually group near-duplicate events on this calendar. Default when never set: `true` for `kind=subscribed`, `false` for `kind=local`. The server only stores and returns the flag; the grouping itself is client-side.
- `DELETE /calendars/:id` → `{ok:true}`. Deletes the calendar and its events outright; the Activity snapshot lets `POST /undo` (or the entry's undo) restore them within the 7-day window.
- `POST /calendars/:id/adopt` → calendar object. Turns a subscribed calendar (ICS or Google) into a local one, one-way: the source link goes, polling and write-through stop, every event becomes an editable local event as last synced, and an `opportunities` role becomes `mine`. 400 for a calendar that is not subscribed.
- `POST /calendars/subscribe` `{url,name?,color?}` → calendar object (201); server fetches immediately, then polls hourly. A bearer-created subscription remains active only while that exact API token is live.
- `POST /calendars/:id/refresh` → `{ok:true, imported:N}` (force poll now); 502 `feed_fetch_failed` when the fetch itself fails. A paused subscription returns 409 `subscription_authorization_revoked` without fetching.
- `POST /calendars/:id/claim-subscription` → calendar object. Session only. Explicitly makes a paused legacy or token-created ICS subscription account-owned and resumes polling without changing its cached events or source URL.
- `POST /calendars/import` multipart file `ics` + `name?` → calendar object + `{imported:N}` (201). 413 `import_too_large` when the file is over `IMPORT_BYTES` (25 MiB), holds more events than `IMPORT_EVENTS` (20,000), or carries more skipped occurrences (EXDATE values) than `EXDATE_VALUES_PER_EVENT` (1,024 per event) or `EXDATE_VALUES_PER_INPUT` (4,096 per file), checked on the raw text before it is parsed; the event cap is lowered to what the PHP process's `memory_limit` can hold, and the message says which limit applied. Descriptions over 65,535 characters and URLs over 2,048 are cut, and control characters never enter a UID or URL (on every ingest path, this one, feeds, CalDAV, mail and `POST`/`PATCH /events` alike). All such budgets live in `server/src/Support/Limits.php` with `BETTERCAL_LIMIT_*` overrides (the two EXDATE budgets can be raised only to hard ceilings of 2,048 and 8,192).
- `POST /folders` `{name}` (201) / `PATCH /folders/:id` / `DELETE /folders/:id`.

## Google Calendar
Read side of the Google connector (`docs/google-calendar.md`). Consent is a browser round trip, not an XHR.
- `GET /google/status` → `{configured:boolean, accounts:[{id,email,status:"ok"|"error",reauthRequired:boolean,error,connectedAt,unfinishedMoves:[{calendarName,status,done,total}]}]}`. `unfinishedMoves` lists moves to Google on that account that are queued, running or failed; disconnecting cancels them. `configured` is false until the server has `BETTERCAL_GOOGLE_CLIENT_ID` / `_SECRET`. `reauthRequired` means an explicit compromise reset quarantined the credential; cached calendars remain but polling and writes stay paused until reconnection.
- `POST /google/connect` → `{url}` for Google's consent screen (calendar read + event write scopes, plus email). Session + CSRF + recent password confirmation required. `GET` remains as a compatibility redirect but enforces the same recent-password rule.
- `GET /google/callback?code&state` → 302 to `/google?connected=1` or `/google?error=<code>` (`denied|google|state|failed`; the client shows fixed text per code, never words from the URL) (a handoff path the client turns into Settings, Connections, plus a toast). A cookie session is required. `state` is HMAC-bound to that exact initiating session and expires in 10 minutes; the session is checked again under a database lock before the credential is stored, so a concurrent password reset wins safely. Reconnecting an email that is already connected replaces its token and clears its quarantine without changing its account id or calendar links.
- `POST /google/accounts/:id/disconnect` → `{ok:true}`. Session only. Revokes at Google (best effort) and forgets the token; calendars subscribed from it stay and report "Google account disconnected" on their next poll.
- `GET /google/accounts/:id/calendars` → `{calendars:[{id,name,accessRole,primary,color,kind,calendarId}]}`: Google's calendar list for the account, sorted by `kind` (`yours` | `shared` | `feed` | `google`, derived from the calendar id and role since Google states only a role), `calendarId` being our calendar id when already subscribed. Session only; a bearer token cannot spend the connected Google credential. 502 `google_unavailable` when Google does not answer.
- `POST /google/accounts/:id/subscribe` `{googleCalendarId,name?,color?,folderIds?,accessRole?}` → calendar object (201), synced immediately; 409 `already_subscribed` or `session_revoked`. `accessRole` (from the list) decides `editable`. Session + recent password confirmation required; the exact initiating session is locked and rechecked when the subscription is saved, so a request revoked by a concurrent compromise reset cannot resume after reconnection.
- `POST /calendars/:id/move-to-google` `{accountId, googleCalendarId?}` → move `{id, googleAccountId, status: queued|running|done|failed, cancelled, stoppedByOwner, stoppedByUpgrade, total, done, error, createdNew, googleCalendarId}`. Moves a local calendar into the account: creates a Google calendar (or uses `googleCalendarId`, which the account must own or be able to edit and which isn't already a calendar here), uploads every event with Google's import call, then turns the calendar into a Google-backed one (write-through). The request may do the first bounded slice; larger moves continue in the worker. A database lease allows only one executor, and opaque recovery markers let a retry recover a newly created Google calendar or an accepted event import after response loss instead of creating another. Calling it again after an ordinary failure continues with the original account and target. A compromise-reset cancellation sets `cancelled:true` and is never resumed implicitly; an explicitly configured later move is a new attempt. An unfinished pre-integrity-upgrade move is also cancelled rather than resumed from ambiguous remote state. 409 `google_reconnect_needed` when the account is quarantined or creating needs the `calendar.app.created` scope the account hasn't granted (reconnect it); 409 `google_calendar_in_use`; 409 `session_revoked` if a concurrent reset ended the initiating session before the move was durably created. While a move is queued, running, or failed but retryable, snapshot-changing writes are refused with 409 `calendar_moving`; local-only metadata such as tags and reminders remains writable. Session + recent password confirmation required, rechecked under lock when the move is saved.
- `DELETE /calendars/:id/move-to-google` → the cancelled move. Stops an ordinary failed move and makes the local calendar editable again. Any partial copy already created at Google is left for the owner to review or remove there. Session + recent password confirmation required.
- `GET /calendars/:id/move-to-google` → `{move}`: the calendar's latest move, or null. Accounts in `GET /google/status` carry `canCreateCalendars`.
- Writes to an `editable` Google calendar go through `POST /events`, `PATCH /events/:id` and `DELETE /events/:id` as usual and reach Google before they return. Errors: 502 `google_write_failed` (Google refused or is unreachable; nothing changed), 403 `google_write_failed` (the account may not edit that calendar), 409 `google_unsynced` (the row has no Google id yet; refresh the calendar), 403 `google_move` (moving between a Google calendar and another calendar), 403 `google_trip_move`, 409 `google_disconnected`, or 409 `google_reconnect_needed` while a compromise quarantine is active. The calendar polls every 5 minutes by default (one sync-token request when nothing changed) and refreshes through `POST /calendars/:id/refresh` like any feed.

## Events
- `GET /events?start=ISO&end=ISO&calendars=1,2&q=&includeHidden=0` → `{events:[occurrence...], capped?:[eventId...]}`. A window longer than two years is refused with 400; ask for longer spans in pieces. A repeating series expands to at most 1,000 occurrences per request (`Recurrence::MAX_INSTANCES`); a series with more in the window shows its first 1,000 and its master event id is listed in `capped`, which is present only then (see [limits.md](limits.md)). Occurrence: `{instanceId, eventId, calendarId, uid, title, description, location, locationLat, locationLng, geocodedAt, url, start, end, allDay, tzid, recurring:boolean, rrule, source, attendance, status, score, feedback, reminders:[], reminderSource, tags:[], people:[], isContainer:boolean, containers:[{eventId,title}], styleJson, createdAt, updatedAt, isNew:boolean}` **Two shapes, one type.** Single-event responses (`GET /events/:id/occurrence`, the object returned by `POST /events`) carry the full record above. List responses (`GET /events`, `/search`, `/people/:id/events`, `/events/:id/links`) carry grid occurrences: the full record **minus `uid`, `createdAt`, `updatedAt`, `reminders`, `reminderSource`, `rrule`, `description`, `tzid` and `geocodedAt`** (the last is when the background sweep last tried to place the address; set with `locationLat` null means it could not), with **null-valued fields and empty lists omitted** rather than sent as `"key":null` / `"key":[]` (a missing key reads as null or `[]`; `false`, `0` and `""` are still sent; `recurring` stays so a row can say it repeats without carrying the rule; `hasReminders` and `hasDescription` are sent as `true` only when true, so a client can reserve space for what the record will fill in). Thousands of rows travel as the list shape, so it carries what the grid draws (#15). A client that shows any of the omitted fields fetches the single-event record on open and merges only those fields: for a recurring instance the record is the row's serialization, so its `start`/`end`/`instanceId` are the master's, not the occurrence's. `isContainer` marks trip events; `containers` lists the trips this event is attached to as `{eventId, title}` pairs (usually 0 or 1 — the schema is n:m but v1 UX keeps one trip per event). Both are batch-loaded server-side (like tags); see Trips below. `reminders` is the event's *effective* reminder list (override if set, else the calendar default, else the global default) and `reminderSource` says where it came from: `"event"|"calendar"|"default"`. Entries are `{minutes:int}` (offset before start; before local midnight for all-day events) or, for inherited all-day defaults, `{daysBefore:int, time:"HH:MM"}`. See Reminders below. `locationLat`/`locationLng` are numbers or null (stored coordinates for the free-text location; the client stores them directly when the user picks a candidate from `GET /geocode/search`, and otherwise resolves them lazily via `GET /geocode` and PATCHes them back onto local events). `rrule` is the master's raw RRULE string or null (present on every expanded occurrence of a recurring master; null on overrides) — clients use it for the human-readable recurrence description in the detail view. `score` is a number 0-1 or null: the background trainable-ranking score (feed events only; null until the worker has scored the event or while fewer than 5 feedback signals exist). Clients sort by it client-side; the API's order is unchanged. `feedback` is `"up"`, `"down"` or null: the event's current thumbs state (its newest signal, from the thumbs or from attendance triage), read for feed events only. Additive fields: occurrences matching an enabled `dim` filter carry `"dimmed": true`, occurrences matching an enabled `highlight` filter carry `"highlighted": true` (and, on `/events`, `highlightColor` when the winning filter has a `color`); the fields are absent otherwise. Occurrences matching an enabled `hide` filter are omitted from `/events` and `/search` responses entirely. Prompt-filter verdicts (see Filters) feed the same mechanics with the same precedence (hide beats dim beats highlight). `includeHidden=1` returns occurrences normal responses omit: `attendance:"hidden"` events AND occurrences an enabled `hide` filter (keyword/regex or prompt) would drop. Reminders fire regardless of filters, so the notification deep-link handler uses this to resolve the occurrence a notification points at. `q=` matches title/description/location as a substring and also tag names; a `q` equal to or prefixed with `#` (e.g. `#work`) matches tags only. Same treatment as `/search`. `start`/`end` are ISO8601 with offset. Recurring events arrive pre-expanded; `instanceId = eventId + ":" + occurrenceStartUtc` where occurrenceStartUtc uses compact UTC basic format `YYYYMMDDTHHMMSSZ` (e.g. `42:20260801T190000Z`). This format is FROZEN; clients treat instanceId as opaque and use the occurrence's `start` field when an API call needs `instanceStart`.
- `POST /events` `{calendarId,title,start,end,allDay?,tzid?,description?,location?,locationLat?,locationLng?,url?,status?,rrule?,tagNames?,personIds?,personNames?,isContainer?,reminders?}` → occurrence (first instance), 201. `status` is `confirmed` (default), `tentative` or `cancelled`. A weekly `rrule` whose `BYDAY` does not list the start's weekday moves the start (and end) forward to the first listed day, keeping the time. `locationLat`/`locationLng` (numbers or null) store coordinates directly when the client picked a place from `GET /geocode/search`; omitted/null means "resolve in the background": the worker's geocode sweep runs every minute and fills in coordinates for any event (local or feed) that has a location and none yet, upcoming first, one network lookup per second, identical addresses looked up once. A feed poll that changes an event's location clears its coordinates for re-resolution. The detail view still geocodes on open as a fallback for anything the sweep has not reached. **People: prefer `personIds`.** `personIds` (list of person ids from `GET /people`) sets the event's people authoritatively and is what the app's own editor sends. `personNames` upserts by name instead, creating anyone it does not recognise; it exists for callers that only ever have names (ICS import, mail ingest, quick-add) and have nobody to ask. Sending both unions them, which is how a client attaches known people alongside one genuinely new name. Ids not owned by the caller are dropped rather than trusted. Names are lossy across a rename: a name-keyed save cannot tell "new person" from "my copy of this name is stale", and resolves that by creating a duplicate — so a client that caches occurrences (which carry people as display names) must map back to ids before writing, not replay the names. `description` is ONE field holding either plain text or rich HTML (the editor writes HTML). The server sanitizes any markup on create/PATCH through an allowlist (`p, br, b, strong, i, em, u, a[href http/https], ul, ol, li, div`; all attributes, styles, classes and script-bearing tags stripped, unknown tags unwrapped to their text). Plain text without markup is stored verbatim. Clients render descriptions containing tags as sanitized HTML and plain text with line breaks otherwise.
- `PATCH /events/:id` body same fields plus `{locationLat?, locationLng?}` (numbers or null) and `{scope:"this"|"following"|"all", instanceStart?}` (scope required when event is recurring) → `{ok:true}`. A `calendarId` change on a series honours the scope: `"this"` detaches that occurrence as a standalone event on the target calendar (new uid; the series skips the day), `"following"` splits the series and the new series lives on the target, `"all"` moves the series and its exceptions together. An override row patched with `calendarId` detaches the same way. `scope:"all"` with `instanceStart` (what the web editor sends when a series is edited from one occurrence) changes the series by what changed for that occurrence: the same number of days (a weekly `BYDAY` shifts with it unless the edit sends its own `rrule`), the new time of day, zone and length. Without `instanceStart`, `start`/`end` set the series' own first occurrence. Either way, when a series moves (start, zone or all-day flag) with its repeat days unchanged, its skipped dates and edited occurrences keep their places in it, as does a timed `UNTIL` unless the edit sends its own `rrule`; when its repeat days themselves change, it restarts on its first listed day. `reminders`: list of `{minutes:int}` (0-40320, max 5, normalized unique/ascending) sets a per-event override; `[]` means explicitly no reminders; `null` clears the override back to inherited defaults. Like attendance and tags, `reminders` is accepted on feed events (it is user-local metadata and survives feed polls). `isContainer` (boolean) sets or clears the trip flag. Clearing requires the trip to have no attached members, else 400 `trip_has_members` (detach them first). Feed events cannot become trips (`isContainer` counts as a content edit → 403 `feed_readonly`), though they can be trip members.
- `DELETE /events/:id` `{scope?,instanceStart?}` (body or query) → `{ok:true}`. On a series `scope` defaults to `"all"`. Feed events refuse with 403 `feed_readonly` (hide them instead). Deleting a trip detaches its members — they survive on their own calendars; only the links go. "Delete trip and its events" is a client-side two-step: the client deletes each member first (after the user picks that option in the confirm), then the trip itself.
- `POST /events/:id/copy` `{calendarId, scope?:"this"|"all", instanceStart?}` → the new event's occurrence (201). A copy is a new event on the target calendar with the same content, tags, people, reminders and coordinates and, for `scope:"all"` on a series, the recurrence rule and skipped dates; `scope:"this"` copies one occurrence as a plain event. Fresh uid; no Google event link. Goes through the create path, so a Google-backed target is written through and a non-editable target is refused (`feed_readonly`). This is the supported way across the Google boundary today: copy, then delete the original.
- A timed occurrence with `relationship: context` carries `tzid`, its own zone, so a client can show a place-bound moment (a sunset, a tide) in that zone with the zone named when it reads differently from the device's. Other list-shape occurrences leave `tzid` to the single-event record.
- Every occurrence carries `icon` (a host icon name or one glyph, or null): set per event by a plugin through `syncEvents`, shown on context tokens (`docs/relationships.md`, "Where context is drawn"). Events from feeds and the editor have none.
- Every occurrence carries `relationship` (concept and UI: `docs/relationships.md`): `planned` | `maybe` | `available` | `context` | `hidden`, derived from the calendar's `role` and the row's own marks (`attendance`, `status`): context calendars are always `context`; `attendance` going/interested/hidden win; on a `mine` calendar a tentative event is `maybe`, otherwise `planned`; on an opportunities calendar the rest is `available`.
- `POST /events/:id/relationship` `{relationship:"planned"|"maybe"|"available"|"hidden", scope?, instanceStart?}` → `{ok:true}`. On a `mine` calendar only planned|maybe are valid and they set the event's `status` (confirmed|tentative), which CalDAV clients and Google see; on an opportunities calendar they set the private attendance mark. Context calendars refuse. This is the one endpoint a client needs; the two below remain.
- `POST /events/:id/attendance` `{attendance:"none"|"interested"|"going"|"hidden" (or planned|maybe|available), scope?:"this"|"following"|"all", instanceStart?}` → `{ok:true}`. On a series, `scope:"this"` gives that occurrence its own row (an override differing only in attendance; feed and Google polls leave a person's own overrides alone), `"following"` splits the series there, `"all"` (default) sets the master and every override. A hidden override hides just its day. On feed events an attendance change also auto-records a ranking feedback signal (`going`/`interested` → up, `hidden` → down; `none` records nothing).
- `POST /events/:id/feedback` `{signal:"up"|"down"}` → `{ok:true, feedback}` (the event's feedback after the call). Explicit thumbs feedback (distinct from attendance); accumulates as training signal for background ranking. The newest signal is the event's current one, so repeating it is ignored and the other thumb switches it. Not undoable.
- `POST /quickadd` `{text, tz, commit?:boolean, calendarId?}` → `{draft:{title,start,end,allDay,location,personNames:[],calendarId,confidence,source:"llm"|"fallback",modelLimit?}}`; if `commit:true` also creates and returns `{event}`, with 201. Parsing is deterministic-first: the fallback parser always runs, and the LLM is consulted only per the `nlParseMode` setting (see Settings). `smart` (default): the LLM runs only when the deterministic parse is incomplete (no resolved date+time / date+allDay) or its confidence is below 0.75 — a complete confident parse returns immediately with `source:"fallback"`. `always`: LLM-first with deterministic fallback on failure. `never`: deterministic only. LLM failure never blocks; the fallback draft is returned. Model-assisted previews and commits share persistent account/token budgets; when capacity is reached, `modelLimit:{code,message,retryAt}` explains why the returned draft used the basic parser. Text over the configured 4,000-character default returns 413 `quickadd_text_too_long` before parsing or model dispatch.
- `POST /undo` → `{ok:true, undone:{entity,op}}` or 404 `nothing_to_undo`. Undoes the most recent create, update or delete not yet undone; log-only entries (changes sent to Google, feed-poll summaries) are passed over. A specific entry is undone with `POST /activity/:id/undo`.

## Trips (event links)
A trip (docs/design-containers.md) is a normal event with `isContainer:true` that groups other events via the `event_links` table. Attachment is a relationship, not ownership: members keep their own calendar, colors, times and lifecycle. Feed events can be members (the link is user-local metadata, like tags and reminders, and survives feed polls). Same-calendar membership works exactly like cross-calendar membership. One nesting level only: a trip can never be attached to another trip. The schema permits an event in several trips; v1 UX restricts to one. Span growth is a client concern: attaching an event outside the trip's dates prompts "Extend trip to include this?" — the server never grows the span silently.
- `POST /events/:id/links` `{eventId}` → `{ok:true}` (201). Attaches `eventId` to trip `:id`. 400 `trip_invalid` when `:id` is not a trip, when `eventId` is itself a trip, or on self-attach; idempotent no-op when already attached; 404 when either event is missing or not yours.
- `DELETE /events/:id/links/:eventId` → `{ok:true}`; 404 when the event is not attached.
- `GET /events/:id/links` → `{events:[occurrence...]}` — every member of the trip, chronological by start (flights out and back land first and last naturally). Deliberately non-windowed: the trip detail view needs the full list regardless of the visible range. Recurring members appear once as their master occurrence, not expanded. 400 `trip_invalid` when `:id` is not a trip.
- `PATCH /events/:id` on a trip with `moveMembers:true` and a new `start` moves the whole trip: every attached member shifts by the same number of days (plus any change in the trip's time of day) on its own calendar, keeping its wall-clock times, in one undo entry. On a Google calendar this is refused with 403 `google_trip_move`.
- Attach/detach are undoable via `POST /undo` (entity `event_links`) and journal a CalDAV MODIFY on both the trip's and the member's calendar objects so DAV clients refresh their `RELATED-TO` lines.
- CalDAV/ICS export: a trip VEVENT carries one `RELATED-TO;RELTYPE=CHILD:<member-uid>` line per member, and each member VEVENT carries `RELATED-TO;RELTYPE=PARENT:<trip-uid>` (RFC 5545; survives round-trips with clients that preserve the property, degrades harmlessly elsewhere). Outbound `/feed/{token}.ics` gets the same treatment. ICS/feed **import ignores `RELATED-TO`** for now: trip membership is created only through this API, never from inbound calendar data.

## Search
- `GET /changes/cursor` → `{cursor}` — opaque string that changes whenever the user's events change (via calendar synctokens: API, CalDAV, feed polls, mail ingest, RSVP) or availability spans or people are added or removed. Editing an existing span or renaming a person does not move it. Clients poll it (~30s while visible, immediately on focus/online) and refetch the window + people + availability only when it moves.
- `GET /search?q=text&limit=50&when=all&calendar=` → `{results:[occurrence...]}` (FULLTEXT, past included, ranked by relevance, then newest first; `limit` clamped 1-200). `when` is `all` (default), `upcoming` or `past`, applied before the limit; `calendar` narrows to one calendar id. Each result carries `upcoming` (boolean; a repeating series counts until its `UNTIL`, and an upcoming one shows its next occurrence); with `when=upcoming` the response also carries `pastCount`. Tag names and people names match too; `#term` searches tags only, `@term` searches people only.
- `GET /people` → `{people:[{id, name, notes, eventCount, nextStart}]}` — everyone, whether or not linked to events (alphabetical; `eventCount` counts undeleted events, `nextStart` is the soonest future start in UTC ISO or null). People rows are created explicitly via `POST /people` (below), or implicitly by `personNames` on event create/patch and by quick-add "with X" clauses. The app's own editor always creates explicitly and then links by `personIds`, so that a name it does not recognise becomes a question rather than a silent new person.
- `PATCH /people/:id` `{name?, notes?}` → `{id, name, notes, showOnCalendar}`. Renaming onto an existing person's name MERGES the two (links move to the survivor, the renamed row is deleted, the survivor is returned).
- `DELETE /people/:id` → `{ok:true}` — removes the person and their event links; events are untouched.
- `GET /people/:id/events` → `{results:[occurrence...]}` — that person's events (undeleted, newest first, limit 200), same shape as `/search` results.
- `POST /people` `{name, notes?}` → `{id, name, notes, created}` (201 when new; returns the existing person with `created:false` when the name is already taken — idempotent explicit creation for the People page and New menu).
- People availability (docs/design-availability.md): `GET /people` rows also carry `showOnCalendar`, `currentSpan` (the away/busy span covering now, or null) and `nextSpan`; `PATCH /people/:id` accepts `showOnCalendar`. Spans: `GET /people/:id/availability` → `{spans:[{id, personId, start, end, kind:"away"|"busy", note}]}` (start/end UTC ISO, end exclusive); `POST /people/:id/availability` `{start, end, kind?, note?}` → span (201; kind defaults to away); `PATCH /people/:id/availability/:spanId` `{start?, end?, kind?}` → span; `DELETE /people/:id/availability/:spanId`. `GET /availability?start&end` → `{spans:[span + name]}` for people with `showOnCalendar` (calendar bands). `GET /availability/check?start&end&names=A,B` → `{conflicts:[span + name]}` overlapping spans for the named people regardless of visibility (editor scheduling assist).
- Occurrences carry `dupes` (omitted when empty): `[{pairId, eventId, calendarId, groupId}]`, the same event on other calendars (#9), linked by series for an occurrence override. `groupId` identifies the complete sparse linked group even when its hub is outside the current window. A client shows each linked group once among what is visible: the copy from the most live source (Google, then local calendars, then feeds, then a booking read from mail; ties to the one with a location and description). `POST /duplicates/:pairId {status: linked|dismissed}` records the owner's word on a pair (`dismissed` shows both again and the scan never proposes them again). A background scan (every 10 minutes) links copies with the same UID on two calendars, or the same title at the same moment on two calendars (not a lone generic word like "Lunch"); looser matches (near in time, similar titles, one calendar holding the same thing twice) wait in Review. Copy to marks the copy and its source as distinct. Of a linked group, only one copy's reminders fire: the best-ranked one that has any.
- Occurrences carry `invite` (nullable): `{kind: invitation|booking, via: mail|google, method, organizer:{email,name}|null, attendees:[{email,name,partstat}], sequence, myPartstat, canReply, why, whyCode, reply?}` (docs/email-ingest.md, docs/google-calendar.md#invitations). A `booking` (a reservation or ticket read from mail) has nothing to answer. `canReply` is false with `why` (text) and `whyCode` (`cancelled|not_request|no_organizer|not_configured|address_mismatch`) when an invitation can't be answered here. `reply` is the last mail reply's outcome `{partstat, sent, reason, message, at}`. `POST /events/:id/rsvp` `{answer: accepted|tentative|declined}` → `{myPartstat, sent, reason, message}`: by mail, the answer is recorded whatever happens and `sent:false` comes with `reason` (a `whyCode`, or `send_failed`) and `message`; for `via: google` it is set at Google, and a failure is an error response with nothing changed. 400 for a booking.
- `POST /quickadd` with a pasted Google Calendar template link (`calendar.google.com/calendar/render?...` or `/r/eventedit?...`) parses the link's own parameters (`text/dates/details/location/ctz/recur`) into the draft (`source:"gcal-link"`, includes `description` and `rrule`); `commit:true` creates it. The `/add` SPA path feeds the same parser (browser-extension redirect target), `/subscribe?url=` prefills the subscribe drawer (webcal handled), `/share` is the Web Share Target (a `POST` of `title/text/url`, answered by the service worker; the server answers a stray `POST /share` with a 303 to `/`), `/import` + the manifest file handler accept .ics files. None of these payloads is read from the address bar: the shell's head script moves a deep-link path and query into `sessionStorage` and rewrites the address to `/` before the first asset request, and the worker parks a share in a cache entry and redirects to `/`, so a shared link or a feed URL never appears in a request line or a Referer (`web/src/app/handoff.js`). The HTML is served with `Referrer-Policy: strict-origin-when-cross-origin` (also as a `<meta>`).
- `POST /quickadd` with text reading as an availability statement ("NAME is away|busy|out|gone|traveling DATES", NAME matching an existing person exactly) returns `{draft:{intent:"availability", personId, personName, kind, start, end, allDay, confidence, source}}`; with `commit:true` the span is created and returned as `availability` (201), and no event is made (`event` is absent). Tag names match too (case-insensitive substring over the user's tags, joined via `event_tags`): tag-matched events are included after text-relevance matches. A `q` equal to or prefixed with `#` (e.g. `#work`) searches tags only and returns tag-matched events newest first.

## Geocode
- `GET /geocode?q=free+text+location&lat=&lng=&tz=` → `{lat, lng, display, kind}` (numbers + strings, or all null when nothing was found; `kind` is the provider's place type). Proxies photon.komoot.io (no key, HTTPS only through the outbound policy, 3s timeout, User-Agent `Better-Cal/0.1 (self-hosted)`), single best result. Location bias uses the same precedence as `/geocode/search` (explicit `lat`/`lng` > `tz` centroid > none); with a bias up to 20 candidates are re-ranked by the PlaceSearch order-plus-distance blend before picking the winner, and a winner over 1,500 km from the bias point for a comma-less description of four or more words, when the winner is not itself a place-level feature, counts as not found. Without a bias, same-named places are ranked by significance, and when Photon finds nothing or its best answer is a city or smaller settlement, Open-Meteo's geocoder is asked as well and wins only with a place of 100,000 or more people (it knows English names and population). When the full text finds nothing, easier forms are tried (bracketed parts dropped; from a later street-number part on). A `q` of exactly three uppercase ASCII letters is treated as an IATA airport code and resolved against the vendored OurAirports table (`server/data/iata-airports.php`, ~9k airports, offline and authoritative — Photon cannot resolve IATA codes), falling back to a plain biased query when the code is unknown. Results are cached permanently in `geocode_cache` keyed by a sha256 of the lowercased whitespace-normalized query plus the integer-degree bias cell (same text can resolve differently per region); provider "no result" answers are cached as negative rows, transport failures are returned as not-found but never cached. Empty `q` → 400. The client calls this lazily when the event detail view opens with a location and no stored `locationLat`/`locationLng` (sending `homeLat`/`homeLng` when set, else the event's `tzid`), then PATCHes resolved coordinates onto local events (feed events keep the result transient).
- `GET /geocode/search` with a `q` of exactly three uppercase ASCII letters additionally pins the IATA-table airport above the biased general results (with `distanceKm`/`far` still computed against the bias).
- `GET /geocode/search?q=&lat=&lng=&tz=&limit=6` → `{results:[{name, address, lat, lng, display, city, kind, distanceKm, far}]}` — multi-candidate place autocomplete for location pickers (same Photon proxy, timeout and UA; uncached, limit clamped 1-10, default 6; empty `q` → 400). `address` is a concise composition of street+housenumber, city, state, country (name excluded, repeats deduped); `display` = `name, address`; `city` is nullable. Location bias precedence: explicit `lat`/`lng` (the client sends the `homeLat`/`homeLng` settings when set) > `tz` (an IANA zone id resolved server-side to an approximate centroid; ~60 major zones, unknown zones mean no bias) > none. With a bias, candidates are re-ranked by blending Photon's order with distance and each carries `distanceKm` plus `far: true` beyond 500 km so the UI can flag matches half a world away; without a bias `distanceKm` is null and Photon's order is kept. Transport failures return `{results:[]}`, never an error.

## Filters
Keyword/regex/prompt filters applied server-side to `/events` and `/search`. Keyword = case-insensitive substring; regex = PCRE, evaluated case-insensitively. Regex filters run inside a budget, because the text they match comes from feeds and invitations: each match has a reduced backtracking limit, a pattern that hits it is skipped for the rest of the request, and a request evaluates at most `REGEX_EVALS` (20,000) regex matches. Giving up means "no match", so a `hide` filter fails open (the event shows) rather than stalling the calendar; it is logged server-side. Scope `global` applies to everything, `folder` to every calendar in the folder, `calendar` to that calendar (`scopeId` required for folder/calendar scope). Action `hide` removes matching occurrences; `dim` adds `"dimmed": true` to them; `highlight` adds `"highlighted": true` (accent emphasis client-side). Across all filter types the strongest action wins: `hide` beats `dim` beats `highlight` (an event matching both a hide and a highlight filter is hidden).
- `GET /filters` → `{filters:[{id, scope:"global"|"folder"|"calendar", scopeId, type:"keyword"|"regex"|"prompt", config, action:"hide"|"dim"|"highlight", enabled:boolean}]}`. `config` by type: keyword/regex `{pattern, fields:["title"|"description"|"location"|"tags", ...], color?}`; prompt `{prompt, negativePrompt?, threshold?, color?}`. `color` (a highlight filter's glow) must be one of the ten palette colours in `Filters::HIGHLIGHT_COLORS`. The `tags` field matches the pattern against each of the event's tag names.
- `POST /filters` `{scope, scopeId?, type, config, action?, enabled?}` → filter (201). `config.fields` defaults to title/description/location (`tags` is opt-in). Invalid regex → 400 `filter_invalid_regex`. Prompt: `config.prompt` required (max 2000 chars), `negativePrompt` optional, `threshold` optional number 0-1 (when set, the LLM score decides pass/fail at that cutoff instead of the model's boolean).
- `PATCH /filters/:id` (any of scope, scopeId, type, config, action, enabled) → filter. Changing a prompt filter's type/config invalidates its cached verdicts and re-evaluates in the background.
- `DELETE /filters/:id` → `{ok:true}`.

Prompt filters are never evaluated in the request path. A background worker job (`filter_eval`) scores feed events against the prompt/negative prompt in Gemini batches (≤25 events per call) and caches per-(filter, event) verdicts in `filter_evals`; `/events` and `/search` join that cache and apply the filter's action to events whose verdict is `fail`. Coverage is all in-scope feed events within a wide window — 2 years back to 3 years forward (recurring masters always qualify) — not just future events, so browsing past months is filtered too. Sweeps process up to 500 events per filter per pass and chain follow-up jobs until the window is drained. Evaluation triggers: prompt-filter create/update/enable (catch-up sweep over the whole window), each feed poll that changes events, a nightly catch-up, and on-read healing: when `GET /events` returns feed events that an enabled prompt filter covers but has no cached verdict for, the server enqueues one targeted `filter_eval` job for those event ids (capped at 300 ids per enqueue, deduped by a payload hash against pending/running jobs; works even outside the sweep window). A missing or not-yet-computed verdict is treated as pass — LLM failures never hide events or block responses. Related: a `rank_events` job (hourly and after polls) uses accumulated feedback signals (≥5 required) to score future feed events onto `occurrence.score`.

## Reminders & Web Push

Reminders are a core feature and must fire with the app closed, so delivery is Web Push: the cron worker enqueues a `reminder_scan` job every minute that expands upcoming occurrences (35-day lookahead, recurrence-aware), computes each reminder's fire time, and sends a push to every subscription of the event's owner for reminders due since the last minute (1-hour catch-up grace; nothing older fires). Sent reminders are deduplicated in `notified_instances` keyed `eventId:occurrenceStartUtc:offsetMinutes` (rows pruned after 7 days). The service worker shows the notification (`tag` = instanceId, so re-sends replace rather than stack) and clicking it opens `/?event=instanceId&at=ISO` (`at` = the occurrence's start instant, UTC `YYYY-MM-DDTHH:MM:SSZ`, additive since the `event`-only form), which the app resolves to that event's detail view: it uses the occurrence from its cache when it has it, otherwise loads a window spanning now and `at` when `at` is within 60 days, and, if the occurrence is still missing (a distant target, concurrent view load, hidden attendance, or a hide filter), fetches once a tight `GET /events` window of 36 hours either side of `at` with `includeHidden=1`.

Resolution order per event: the event's `reminders` override (`[]` = explicitly none) > the calendar's `reminderDefaults` > the global `reminderTimed`/`reminderAllDay` settings. Exception: subscribed (feed) and plugin calendars never inherit the global defaults — they only remind when the calendar has explicit `reminderDefaults` or an event has an override, so subscribing to a busy feed or turning on sunsets does not flood notifications. Events with `attendance:"hidden"` or `status:"cancelled"` never remind.

Fire-time semantics: `{minutes}` = minutes before the start instant. `{daysBefore, time}` (all-day defaults) = that wall-clock time, daysBefore days before the event date (e.g. `{daysBefore:1, time:"18:00"}` = 6 PM the evening before). For all-day events the DATE comes from the event, and the clock (midnight for `{minutes}`, the wall-clock `time` otherwise) is the owner's Home zone, the `tz` setting; the event's own tzid is used only when no Home zone is stored. An all-day event is a date, not an instant, so an event imported as UTC reminds at 6 PM where the owner lives, not at 18:00 UTC.

Every event has a `tzid` (IANA zone). For a timed event it is the clock the event lives on: `start`/`end` are serialized with that zone's offset, and a repeating event keeps its wall-clock time in it across DST changes. `start`/`end` on writes are instants (send an offset), so `tzid` never changes WHEN a single event happens, only which clock it is expressed and repeated on. `POST` without `tzid` uses the owner's Home zone (`tz` setting); the web client sends the device's zone, or the zone picked in the editor. `PATCH` leaves `tzid` alone unless it is sent; the web editor sends it only when the owner picks a zone, and then reads the typed Start/End as wall-clock time in that zone. All-day events are dates and are stored one way: UTC midnights with `tzid` `UTC`, whatever `tzid` a write sends. Making a timed event all-day sets its `tzid` to `UTC`; making an all-day event timed without sending a `tzid` gives it the Home zone. On a timed event, `UTC` is what imports write when the source gave no zone, so clients treat it as "unknown" rather than as a place.

All-day `start`/`end` on writes (`POST /events`, `PATCH /events/:id`, and `instanceStart` for an all-day series) are calendar dates: send `"YYYY-MM-DD"` (end exclusive). Any ISO8601 string is accepted and only its date portion is read, so the server's own `"<date>T00:00:00+00:00"` serialization can be sent straight back. The time and offset never move the date. (Older clients that shifted that serialization through a local Date, producing a non-midnight time that sits on a UTC midnight, are still read as the UTC date they meant.)

Delivery channels: the `notifyChannel` setting (see Settings) picks how each due reminder is delivered. `push` (default) = Web Push only; `email` = a reminder email only (to the `notifyEmail` setting when set, else the account address); `both` = both; `push-fallback` = push normally, with an email only when no non-failing subscription exists or every push send that attempt was rejected/gone (a push the service *accepted* but never displayed — device unreachable past the TTL — cannot be detected, so fallback email does not cover it). One `notified_instances` row marks the reminder sent regardless of channel, so retries never double-send after a partial success. Email failures are logged and never block the scan. Reminder emails carry the event title, the local time string, location, and a button deep link (absolute against `BETTERCAL_BASE_URL`).

ICS: file import maps display VALARMs with before-start relative triggers into per-event overrides; export (outbound feeds, CalDAV objects) writes a display VALARM per override entry. Inherited defaults and explicit-none export nothing. Feed polls do not sync VALARMs (user-local overrides must survive polls).

Server config: VAPID keys in `.env` (`BETTERCAL_VAPID_PUBLIC`, `BETTERCAL_VAPID_PRIVATE`, `BETTERCAL_VAPID_SUBJECT`), generated once with `php server/bin/vapid.php --generate`. Sending uses `minishlink/web-push` (composer). Email delivery is optional and separate: SMTP via `BETTERCAL_SMTP_HOST`, `BETTERCAL_SMTP_PORT` (default 587, STARTTLS; 465 = implicit TLS), `BETTERCAL_SMTP_USER`/`BETTERCAL_SMTP_PASS` (only when the relay needs auth), `BETTERCAL_SMTP_FROM` (sender address, display name "Better-Cal"); sending uses `phpmailer/phpmailer` (composer). All SMTP vars optional — email stays off gracefully while host or from is empty.

- `GET /push/key` → `{key:string|null}` (VAPID public key; null when unconfigured).
- `GET /push/status` → `{subscribed:boolean, vapidConfigured:boolean, emailConfigured:boolean}`.
- `GET /health` (no auth) → `{ok:true, db:boolean}`; with a valid session cookie also `time` and `version`. Anonymous callers learn only that the service answers.
- `GET /system/health` → `{rows:[{subject, kind:"job"|"feed"|"push", label, status:"ok"|"failing", firstFailedAt, lastFailedAt, lastOkAt, consecutiveFailures, lastError, alertedAt, endpointHash?}], emailAlerts:{configured, systemTo, accountTo}}` — is background work working. One row per subject: the worker's job types (system-wide: prompt filter evaluation, ranking, mail ingest, reminder scan, geocoding, activity retention, alert emails, duplicate detection), each geocoding provider (`geocoder:<provider>`, system-wide, kind `job`), each subscribed feed (`feed:<calendarId>`), each push device (`push:<subscriptionId>`, with the SHA-256 endpoint identity so the client can tell its own device without disclosing the raw push-service capability). Transitions (working→failing, failing→working) are recorded once each in Activity under source `system`. A failing streak earns **one** email once it has lasted long enough to be real (jobs: 1 hour and 3 consecutive failures; feeds: a day; a device: 6 hours), at most one per subject per day while it persists, and one on recovery. Per-user subjects email the account address; system-wide ones `BETTERCAL_ALERT_EMAIL`, else the first user. Requires SMTP; otherwise `emailAlerts.configured` is false and failures are visible only here and in Activity. The client interrupts for exactly three things: a banner while reminders cannot reach *this* device; one toast at boot when prompt filters are not being evaluated; one toast at boot when a visible calendar's feed is failing.
- `POST /push/subscribe` `{endpoint, keys:{p256dh, auth}, label?, resync?}` → `{ok:true}` (upsert by endpoint; re-subscribing clears failure state). `label` is what the device calls itself (cleaned, at most 80 characters). `resync:true` is the quiet re-registration the app does when it opens: it restores a device a password reset cleared and refreshes its label, but never brings back a device the owner removed or clears a failing state. A device registered with an API token belongs to that exact token: revoking the token removes it, and while the token is expired it is not sent to. A token cannot overwrite a browser-owned or different-token device at the same endpoint (`409 push_subscription_owned_elsewhere`). A device new to the account is written to Activity. A password reset removes every device; the client re-registers its own on sign-in.
- `GET /push/devices` → `{devices:[{id, service, label, endpointHash, createdAt, lastUsedAt, failing, viaToken}]}`; `DELETE /push/devices/:id` → `{ok:true}`. Session-only (`403 session_required` for API tokens). `endpointHash` is sha256 of the endpoint, so a browser can find itself; the endpoint is never returned.
- `POST /push/unsubscribe` `{endpoint}` → `{ok:true}`. A session can remove its account's matching endpoint; an API token can remove only a subscription created by that same token. Ownership mismatches are idempotent no-ops.
- `POST /push/test` → `{ok, sent, failed}`; 400 `push_not_configured` / `no_subscription`.
- `POST /push/test-email` → `{ok:true, to}` (test reminder email to the account address); 501 `email_not_configured` when SMTP is not set up, 400 `email_send_failed` when the relay rejects the send. The two test endpoints share a limit of 5 sends per 10 minutes per account; past it they answer 429 `too_many_requests`.
- Failure handling: gone endpoints (404/410) mark `failing_since`; subscriptions failing for 3+ days are deleted by the worker.

| `homeLat` | number -90..90 or `null` | `null` | home location latitude; with `homeLng`, the bias point for `/geocode/search` |
| `homeLng` | number -180..180 or `null` | `null` | home location longitude |
| `homeLabel` | string (≤200) or `null` | `null` | display name for the home location (Settings page only) |
| `mapStyle` | `streets-v2`\|`dataviz`\|`outdoor-v2`\|`bright-v2` | `streets-v2` | MapTiler raster style for the event detail mini-map; only used when the server has `BETTERCAL_MAPTILER_KEY` configured (see `GET /config`) |

## Saved views
Named snapshots of client view state; `config` is client-defined: `{viewType, visibleCalendarIds, folderCollapse, filterText, hideRel, anchor:"today"|dayKey}`. `hideRel` lists the relationships the Show filter switches off (`planned|maybe|available|context`); absent or empty means show all.
- `GET /views` → `{views:[{id, name, config, position}]}`.
- `POST /views` `{name, config}` → view (201).
- `PATCH /views/:id` `{name?, config?, position?}` → view.
- `DELETE /views/:id` → `{ok:true}`.

## Outbound feeds
- Outbound feeds: a feed URL reads events without signing in, so a feed created with an API token belongs to that token (revoking it deletes the feed; an expired token's feed stops answering), and a token listing feeds sees `url` only for feeds it created (others: `url: null`). Feeds carry `viaToken`. Creation is written to Activity; `seed.php --revoke-tokens` gives every remaining feed a new address.
- Settings: a `notifyEmail` set with an API token is remembered with that token (`notifyEmailToken`, read-only) and reminder mail goes back to the account address once the token is revoked or expires.
- Lost-device recovery (`POST /auth/sign-out-others`) also changes every session-created/legacy feed URL and clears a session-set custom reminder address. Token-created channels stay bound to their separately managed token.
- `GET /outfeeds` → `{feeds:[{id,name,url,scope,description,eventCount,eventLimit}]}` (envelope key is `feeds`). `eventCount` is how many events an all or calendar feed covers (null for a search feed); past `eventLimit` (`BETTERCAL_LIMIT_OUTFEED_EVENTS`, 5,000 by default; 500 for a search feed) the oldest past events are left off first. `POST /outfeeds` `{name, scope:{type:"all"|"calendar"|"search", calendarId?, q?}, description?}` → `{id,name,url,viaToken,scope,description}` (201).
- `DELETE /outfeeds/:id`. A browser session may remove any feed in the account; a bearer token may remove only a feed created by that exact token. Other and nonexistent feed ids both return 404.
- Public: `GET /feed/{token}.ics` (no auth; X-WR-CALNAME + description embedded).
- ICS export (outbound feeds, CalDAV feed objects built by `Ics::buildCalendar`): rich (HTML) descriptions write `DESCRIPTION` as tag-stripped plain text plus `X-ALT-DESC;FMTTYPE=text/html` carrying the sanitized HTML; plain text descriptions export exactly as before. A timed event is written in its own zone (`DTSTART;TZID=...` local time) with a `VTIMEZONE` for each zone used, built from PHP's current zone data as yearly rules starting in 1970; UTC events are written with `Z`, all-day events as `VALUE=DATE`, and a time in the repeated hour when clocks go back as UTC. ICS import is unchanged (descriptions imported as text).

## Plugins & proposals
The ops surface for plugins (writing one: `docs/plugins/authoring.md`). Nothing here runs plugin code except a plugin's own settings validation on save. Plugin mutations require browser-session authentication; bearer tokens may use the read endpoints but cannot enable, configure, run, undo or uninstall plugins.
- `GET /plugins` → `{plugins:[{id, name, version, description, permissions, jobs, settingsSchema, calendarSettingsSchema, eventSettingsSchema, decoration, requires, optional, unmetRequires, errors, installed, enabled, disabledReason, consecutiveFailures, settings, lastRun:{job, at, durationMs, outcome, logTail, runId, undoableMutations}|null}]}`.
- `POST /plugins/:id/enable`, `POST /plugins/:id/disable` → `{ok:true}`. `POST /plugins/:id/uninstall` `{deleteCalendars?}` → `{ok:true, purged}`.
- `PATCH /plugins/:id/settings` (values per `settingsSchema`) → `{settings}`; `PATCH /plugins/:id/calendar-settings/:calendarId` → `{settings}`.
- `POST /plugins/:id/run?job=` → `{queued:[jobId], alreadyQueued:[jobId]}`: queues every job (or the one named) for the worker's next tick. Equal pending/running jobs coalesce; disabled plugins return 409, unknown jobs 400, and persistent rate/capacity exhaustion 429. `GET /plugins/:id/warnings` → `{warnings:[{id, eventId, severity, message, fix, ...}]}`. `POST /plugins/runs/:runId/undo` → `{undone, skipped}`: reverses every change one run made, newest first.
- `GET /plugins/ranges?start&end` → `{plugins:{<id>:{truncated, ranges:[{id, start, end, label, color, detailHtml}]}}}`: overlay bands of enabled plugins, at most 500 per plugin per request (`truncated` says when more exist).
- `GET /events/:id/plugin-data` → `{data:{<pluginId>:{key:value}}}`; `PATCH /events/:id/plugin-data/:pluginId` (values per the plugin's `eventSettingsSchema`; null removes a key) → `{saved}`.
- `GET /proposals?status=open` → `{proposals:[{id, pluginId, sourceKey, title, summary, rationaleHtml, plan, destinations:{trip?,events:[]}, acceptAllowed, acceptError, reviewToken, status, createdAt, decidedAt}]}`. Destinations are resolved local calendars and are part of the reviewed revision. `POST /proposals/:id/accept {reviewToken}` → `{proposal, created, runId}` atomically creates the local events (and optional trip) only if that exact revision is still open. `POST /proposals/:id/reject {reviewToken}` → `{proposal}`. A changed revision returns `409 proposal_changed` without deciding or writing it. `POST /proposals/:id/undo` → `{undone, skipped}` and reopens the proposal only after a complete grouped reversal.

## Review queue
Everything waiting on the owner's decision, as one list of eight kinds: `invite_new` (a first-time emailed REQUEST not yet on the calendar), `invite_change` (an emailed REQUEST/CANCEL for an invitation already on the calendar; held, never applied on arrival, see docs/email-ingest.md), `mail_limit` (a bounded aggregate notice that public-mail automation hit a safety or paid-model limit), `model_limit` (a bounded prompt-filter capacity notice for one calendar), `rsvp` (an invitation with `myPartstat: NEEDS-ACTION` that can be answered from here, from mail or a Google guest list, still ahead, not cancelled), `proposal` (an open plugin proposal), `duplicate` (two events that may be one, `event_duplicates` with status `possible`; detail `{pairId, a:{eventId, title, calendar, allDay, start}, b:{...}}`, actions Same event / Not the same, which post to `/duplicates/:pairId`), and `subscription` (an ICS feed whose automatic updates are paused pending an owner decision; detail `{calendarId, origin}`, action Keep updating). `invite_new`, `invite_change`, `mail_limit` and `model_limit` are stored by the queue (`review_items`); the others are read from where they live.
- `GET /review?status=open|all` → `{count, items:[{key, kind, status, title, summary, createdAt, eventId, link, detail, actions}]}`. `key` is `"<kind>:<id>"`. `status`: `open|accepted|dismissed|gone` (`gone`: the event was deleted; superseded items are not listed). `link` is `{instanceId, at}` for opening the event (same pair a reminder notification carries) or null. `detail` by kind: invite_new `{method:"REQUEST", from, organizer, sequence, start, end, allDay, recurring, location, decidedAt}`; invite_change `{method:"REQUEST"|"CANCEL", from, organizer, sequence, diff:[{field, label, from, to}], decidedAt}` (start/end values are ISO instants, or `YYYY-MM-DD` for all-day; description values are plain-text previews); mail_limit `{reason, count, retryAt, latestSubject, latestFrom}` (bounded latest-message context, not a copy of every refusal); model_limit `{reason, count, retryAt, calendarId, calendarName, latestBatchSize}`; rsvp `{eventId, title, start, end, allDay, recurring, location, organizer, via, invitedCount}`; proposal = the `/proposals` object; subscription `{calendarId, origin}`. Open items sort first, then newest first.
- `actions` is `[{name, label, method, path, body?}]` (paths relative to `/api/v1`): run one by sending `body` (or `{}`) to `path`. Proposal accept/dismiss bodies contain the `reviewToken` for the displayed revision; callers must not replace it with a later token without reviewing the later plan. Decided items have none (an accepted proposal offers `undo`). Every Review action—including dismiss, RSVP, duplicate and proposal actions—is returned only to a browser session and every decision endpoint enforces that rule server-side. Bearer-token callers can list the same items but receive no actions.
- `GET /review/count` → `{count, byKind:{invite_new, invite_change, mail_limit, model_limit, rsvp, proposal, duplicate, subscription}}` (the sidebar badge).
- `POST /review/invitations/:id/accept` → `{item, eventId}`. Atomically creates the event and records the owner-approved organizer. It does not send an RSVP; the created event appears separately as an `rsvp` decision when it can be answered. Competing open first-arrival candidates with the same UID close as superseded.
- `POST /review/invitations/:id/dismiss` → `{item}`. No event is created.
- `POST /review/invite-changes/:id/accept` → `{item, eventId}`. Re-checked against the event as it is now; applied through the same path as `PATCH /events/:id` under source `review` (Activity entry, undoable; `scope:"all"` for a series), and the invitation block with its `SEQUENCE` is stored in the same transaction. `409 review_changed` means the owner edited the event after the email arrived: the calendar stays untouched, the item's differences are refreshed, and the owner can review and try again. `409 review_gone` (event deleted) and `409 review_stale` (a newer version was already applied) close the item. `409 review_decided` if it was already decided.
- `POST /review/invite-changes/:id/dismiss` → `{item}`. The calendar is unchanged; logged in Activity.
- `POST /review/mail-limits/:id/dismiss` → `{item}`. Closes an informational aggregate; it never changes the calendar.
- `POST /review/model-limits/:id/dismiss` → `{item}`. Closes an informational prompt-filter capacity notice; it never changes the calendar.

## Activity log
- Every mutating code path journals to `mutations` via `Undo::record()`, tagged with a request-scoped source (`ActivityContext`): `web` (default), `api` (bearer-token), `caldav`, `quickadd`, `rsvp`, `import`, `feed` (poll rollups, log-only), `mail:imip|markup|gcal-link|llm` (ingest tiers).
- `GET /activity?before=&limit=&sources=&q=` → `{entries:[{id,at,source,entity,entityId,op,summary,details,undone,undoable}], nextBefore}`. Latest-first; `before` is a cursor (entry id), `limit` ≤ 100 (default 50). `sources` is comma-separated from `web,api,caldav,feed,mail,quickadd,rsvp,import,geocode,system,plugin,review,dedup` (`mail` and `plugin` match all `mail:*` / `plugin:*` sources). `q` substring-matches summaries. `undoable` = has snapshots, not undone, within the 7-day window.
- `POST /activity/:id/undo` body `{force?:bool}` → `{ok,undone:{entity,op}}`. Errors: `already_undone`, `not_undoable` (log-only entry: feed rollups, RSVP notes, or snapshots pruned past 7 days), `stale_undo` (newer un-undone mutations exist for the same entity — retry with `force:true` to overwrite them deliberately).
- `GET /events/:id/occurrence` → `{occurrence}` (single serialized occurrence; the Activity page's jump-to-event).
- Retention (worker `activity_prune`, daily): snapshots cleared after 7 days (entries become log-only), rows deleted after 90.
- Feed-poll rollups are one entry per poll with changes: `Feed 'Name': N added, M updated, K removed`, `details.addedTitles` (≤20). Log-only by design — undoing a feed import would be redone by the next poll.

## Misc
- `GET /health` (no auth) → `{ok:true, db}`, plus `time` and `version` for a signed-in session (see Reminders & Web Push).
- `GET /config` (auth) → `{maptilerKey, mapStyle}` — public-safe client configuration, fetched once at boot. `maptilerKey` is the optional MapTiler tile key from `BETTERCAL_MAPTILER_KEY` (null when unset; the mini-map falls back to OSM tiles); `mapStyle` echoes the requesting user's map style setting.

## Frontend state contract (bettercal-ui props)
- Settings is one page with tabs (`general`, `notifications`, `location`, `connections`, `account`, `about`, `system`); `state.settingsTab` picks one (General unless something set it; reset on leaving the page), and `/settings/<tab>` is a handoff path that opens it directly.

bettercal-ui components receive plain occurrence objects (above) plus a `CalendarMeta` map `{id:{color,name,visible}}`, and emit intents: `onCreateRange({start,end,allDay})`, `onMoveEvent({instanceId,newStart,newEnd})`, `onResizeEvent({instanceId,newStart,newEnd,edge})`, `onOpenEvent(instanceId,anchorRect,opts?)` (double-click passes `opts={detail:true}` asking for the full detail view), `onExpandDay(dateISO)`, `onRequestWindow({start,end})` (infinite scroll data demand), `onSetAttendance(occ, attendance)` (agenda triage on feed events), `onFeedback(occ, "up"|"down")` (thumbs training signal on feed events). DayExpand additionally accepts `onOpenDetail(instanceId)` for its per-row open affordance. AgendaList also accepts `sortMode: "time"|"match"` (match mode renders the caller-ordered flat list, see `web/src/lib/rank.js` sortByMatch) and `scrollKey`/`scrollSeq` (each new seq scrolls the day-grouped list to the anchor day). All drag math lives in the library; persistence lives in the app layer.

Near-duplicate grouping is client-side: the app layer runs `web/src/ui/grouping.js` over occurrences from calendars with `groupSimilar=true`, replacing same-day same-calendar title-base duplicates with synthetic group items (`{isGroup:true, instanceId:"group:...", title, count, members:[occurrence...]}`); components render those as stack chips, never drag them, and route their `onOpenEvent` clicks to a group list popover.
