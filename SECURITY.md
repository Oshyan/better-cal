# Security

Better-Cal holds a person's calendar, their contacts, and the credentials that reach their Google account and mail. Reports are taken seriously and answered.

## Reporting a vulnerability

Please do not open a public issue for a security problem.

- Preferred: GitHub private vulnerability reporting on this repository (the "Report a vulnerability" button under the Security tab). It stays private until a fix is out.
- Or email coding@oshyan.com.

Include what you found, how to reproduce it, and what you think it allows. You will get a reply within a few days, an honest assessment, and credit in the fix commit if you want it. There is no bug bounty.

Known residuals, accepted and documented rather than fixed:

- Push enrollment counts fragment-free destinations under the account lock and defaults to 100 devices. Existing distinct devices are retained on upgrade. Delivery remains sequential with a timeout per destination; the enrollment limit is not a hard total delivery-time bound. Mixed-credential aliases are not silently reassigned.
- New `/add` and `/subscribe` links carry private values in URL fragments, which browsers do not send in HTTP requests. Older extensions and saved webcal handlers can still send query links during the transition; clearing them from the address bar cannot undo their initial request or its server log. Fragments are not encryption and remain visible to the browser and page scripts.
- The overall sign-in brake can still be triggered by an attacker controlling 10 or more addresses (cheap with IPv6). While it is on, password sign-ins are refused from addresses that have not signed in during the last 30 days, unless the browser has signed in here before (it carries a device cookie, since 0.2.3). CalDAV devices using API tokens are unaffected. A brand-new device has to wait for the attack to subside; a one-time code to let it in is planned in issue #59.
- Prompt filters and ranking judge events in batches of 25, so one event's text can in principle sway the model's verdicts on the others in its batch. The text is sent as separate, marked data with instructions to judge each event independently. Exact integer IDs, unique results, boolean decisions and finite scores in range are checked, but these checks cannot prove that a model's judgment was independent. Separate calls per event would cost substantially more and are not used.
- `DEV_ISOLATION_MODE=shared` deliberately permits shared Unix, database and PHP identities. In that mode, dev code can reach production files and data. Clone sanitation reduces carried-over credentials but does not create an isolation boundary. `strict` remains the default and checks both read access and production write access; see [docs/install.md](docs/install.md).
- When the deploy script connects as root, it leaves the settings file root-owned, but the app user owns the directory it sits in, so this is not a hard boundary. Deploying as a non-root user with sudo skips that step.

The latest full scan covers the code as of release 0.9.13 (2026-10-06), and its fixes run through 0.9.42. Changes since then have had tests, including regression tests for every fixed finding, and review as they were made, but not yet a full scan; a final scan of the 1.0 release candidate is planned (issue #81). Anything you find is worth telling us about.

## Releases and updates

How code reaches an install, and what has to be true before it does.

**What the app does on its own:** once a day it checks GitHub for a newer release and tells you, with a link to its notes. It never downloads or installs code.

**What `server/bin/update.php` checks before installing anything** (it runs only when you run it):

1. The release is a published, non-prerelease, **immutable** GitHub release of this repository, so its tag and files can't be swapped after publishing.
2. Its manifest matches GitHub's SHA-256 digest and the rules the update notice applies (version, priority, a secure-version floor that never moves backwards).
3. **Its signature verifies.** Each release carries `bettercal-release.sig`, a statement of its version, commit and the SHA-256 of its zip and manifest, signed by a key in `server/config/release-keys.php`. The signed hashes must match the files being installed, and in a git checkout the tag must point at the signed commit.
4. The downloaded zip matches GitHub's SHA-256 digest, and it unpacks only into its own folder: no paths that climb out, no symbolic links, bounded in size.

**The signing keys never touch GitHub.** There are two, and either one can sign: a FIDO2 hardware security key that needs its PIN and a touch, which signs every release, and a key file kept in a password manager for recovery. Releases are signed on the maintainer's machine after GitHub builds the zip, and only after that machine has rebuilt the release from the tagged source and the lock file and found GitHub's zip identical, file for file (0.9.86). For the signed ZIP updater, taking over the release account or build alone is not enough. Before signing, the local manifest must match the downloaded one byte for byte, every library export must match the Git commit recorded in the tagged lockfile, and a bounded ZIP comparison must match the local rebuild without extracting the downloaded archive. The signer uses an explicitly prepared, hash-locked environment with pinned uv-managed Python; ordinary signing does not resolve or download dependencies. A hardware key protects its private key, but malicious software on the signing computer can still substitute a statement during an authorized PIN and touch. Keys can be added or dropped in a release signed by a key already trusted, which is how a lost or exposed key is replaced, and `update.php` says whenever a release does that ([docs/releasing.md](docs/releasing.md#signing)).

**During an update:** one update runs at a time (a database lock, shared by `update.php` and the database update page); the site shows "updating" and the worker pauses (it waits for a running job to finish first); the database is backed up first, by PHP itself; the previous version stays whole beside the new one; and `update.php --rollback` puts both the code and the database back, including after an update that was cut off partway. The newest two previous versions and backups are kept, older ones removed. Backups go in a folder beside the app, readable by its account only, encrypted, with names that can't be guessed. That folder and the previous version's get a deny-all `.htaccess` in case the app sits inside a web root, and the updater warns when it seems to.

**Its own address:** Better-Cal answers only at the host in `BETTERCAL_BASE_URL` and redirects or refuses any other, so files reachable as a folder of another site (`example.com/cal/`, common where hosts store subdomains inside the main web root) can't put it on that site's origin. It needs a domain or subdomain of its own, and a separate hosting user where it shares an account with other sites ([docs/install.md](docs/install.md#choosing-where-to-put-it)). Where a host only lets a subdomain point inside the main site's web root, the private files protect themselves (below), and a `.htaccess` at the top of the app folder refuses every request for anything in it except `server/public` on servers that read one (Apache and LiteSpeed).

**Private files on any host (0.9.83):** every file Better-Cal writes that holds a secret ends in `.php` and starts with `<?php __halt_compiler();`, so a server that runs PHP returns an empty page for it: the settings file (`.env.php`), the one-time setup code, the update record, the private-files check's result and PHP's error log. They're always read as text, never included, so no value can break the guard. Database backups are encrypted with libsodium's secretstream (XChaCha20-Poly1305) under a key derived from the session secret, and a restore checks the whole file before it changes anything. The key comes from the settings file, so encryption protects a backup only while that file stays private: it covers a server that hands out the backups but not the settings. Only `index.php` and `dav.php` run from the web (0.9.82). A self-check asks the install's main domain for a probe file in the app folder and reports in Settings, System whether the settings could be downloaded there ([docs/install.md](docs/install.md#keeping-private-files-private)). The one case none of this covers is a server that hands out `.php` files as text and ignores `.htaccess`; the self-check reports exactly that case as "Fix this now".

**First install:** `server/bin/install.php` writes `.env.php` readable by its owner only, with a freshly generated session secret, and never replaces existing settings.

**Setup and database updates in the browser** (for hosting without a command line): a fresh install with no settings file shows a setup page on every path, and an install whose new files have database changes waiting shows a database update page. Both run before anyone can sign in, so both first ask for a one-time code written to `better-cal-code.php` in the app folder (guarded like the settings file): only someone who can read the server's files gets past the first screen, which keeps a stranger who finds a new install first from setting it up for themselves. The code is 60 bits, expires after an hour and works once. Wrong tries never replace it or delay the request, so a stranger sending wrong codes cannot trigger a lockout or deliberately park PHP workers. The first successful entry consumes the code; entering it again does not replace the existing session. The page explains how to reset access by deleting better-cal-code.php if the browser lost its session. Code and session state share one guarded file, with a separate stable lock. Older in-progress code state is replaced, not converted. It starts a session that lasts an hour, in an HttpOnly, SameSite=Strict cookie, and every form carries a token derived from it. Before the code is entered, the page says only which of the two it is (setup, or a database update waiting); over plain HTTP it warns that what's typed travels unencrypted. The pages send a strict Content-Security-Policy and can't be framed. Setup exists only while there are no settings: once it writes `.env.php`, that code path is never reached again, and it refuses a database that already holds an account. The database update backs up first and shows "updating" to everyone else while it runs. If its request is cut off (a host's time limit), the page takes over again, to run it again or restore that backup. While changes wait, or when older files were put back over a database a newer version updated, the API and CalDAV refuse with 503 rather than run against a schema the code wasn't written for.

**Third-party browser code:** the libraries under `web/vendor/` (Preact, htm, Squire, DOMPurify, Leaflet) are the published npm releases, some minified, changed only where [web/vendor/README.md](web/vendor/README.md) says (two one-line edits to Preact's files). Each is pinned by SHA-256 in `web/vendor/manifest.json`, every deploy checks the tree against those pins, and `node scripts/vendor.mjs --check-upstream` re-downloads each release and confirms the committed file matches it. The PHP libraries are pinned in `server/composer.lock` and checked against the Packagist advisory database on every push and deploy.

**Limits, stated plainly:**

- The update notice is signature-checked since 0.9.86: a release is announced, and its security floor recorded, only when its signature verifies. Someone controlling the GitHub account can still hide new releases from installs that haven't seen them yet; nothing signed and time-stamped says how new the newest release is.
- Release notes are not signed (GitHub lets them be edited after publishing). `update.php` labels them unsigned and removes terminal control characters, and still shows them only after the release signature verifies.
- In a git checkout, `update.php` checks the tag against the signed commit, but `composer install` then fetches the PHP libraries from Packagist and GitHub, outside the signature. The zip carries them inside it.
- Updating from 0.9.74 to 0.9.75 used the 0.9.74 updater, which predates signatures. From 0.9.75 on, every update is checked.
- Fresh installs and updates by hand skip signature verification unless you do it yourself before running the downloaded code. A file-manager upload cannot authenticate itself. A first install without an independently trusted verifier and key is trust-on-first-use; a verifier supplied inside the same untrusted ZIP cannot prove that ZIP is genuine. [Optional local verification](docs/install.md#optional-verification-before-upload) needs no SSH on the host.
- If file locking reports failure, setup and database updates continue using atomic single-file writes and log the limitation without a page warning. Concurrent requests may then race. A filesystem that silently ignores locks has the same limitation; the app cannot reliably detect that. Sequential code replay is still refused. This is not a general denial-of-service defense.
- On shared hosting, PHP can usually write to the app's own files, so anyone who can run PHP as that account can change the code. That's inherent in this kind of hosting, and why an update needs nothing more than that account.
- The deny-all `.htaccess` files work only on servers that read them; with Nginx, the guard lines and encryption are what protect the private files. The self-check covers the main domain at the place it would serve the folder, not every domain on a hosting account.

## Design trade-offs

### Private exports and database recovery

New database backups require a non-empty `BETTERCAL_SESSION_SECRET`; there is no plaintext fallback. Settings, System checks this independently of the cached private-files probe and offers a generated settings line. The database update page offers the same repair before starting an update. The app never writes this setting automatically. If a previously configured secret was lost, restore that original value instead: changing it makes older encrypted backups and sealed credentials unreadable. Older plaintext backups remain readable for recovery.

Backup paths and their entries must be real, owned directories and regular files, without symbolic links or hard-linked files. They are checked before permission changes, encryption, writes or pruning. Run conversion as the storage owner, not root inside an application-controlled tree. These checks do not protect against malicious code already running as the same account or a host administrator.

Export and backup storage allow group-writable parents when the group matches PHP's effective group. This trusts the host to keep that account group private; matching group IDs do not prove exclusive membership. Without the optional POSIX functions, group-writable parents are allowed and group isolation is left to the host. World-writable parents without the sticky bit are refused. The sticky bit permits shared temporary directories without allowing other users to replace owned children. Root still refuses any parent owned by another account.

Database restore takes the same update and worker locks as updating. If a worker still holds its lock, restore changes nothing and offers a manual retry. Maintenance stays on after a failed or interrupted restore, with a retry form on the database update page. Filesystem ownership and MySQL named locks must work correctly for these boundaries to hold.

Calendar exports remain session-only and have no event cap. Single calendars stream from bounded database batches without a data file. Account exports spool each calendar and a native ZIP under `.runtime-cache/exports` with owner-only permissions and random 128-bit names. A nonblocking lock permits one export at a time. Cleanup runs on completion, failure and shutdown, with abandoned files removed under the next export's lock. ZIP contents are finished before download; a failed direct stream has no closing calendar marker and must be downloaded again. Memory grows with a batch, an individual event and ZIP directory metadata, not the whole event collection. Disk space and host-enforced request limits can still stop an export; nothing is silently omitted to fit.

Export spools are not encrypted or PHP-guarded. Keep the cache outside publicly served folders or deny access to it. On a misconfigured host, a web server with the same account could serve a spool if its random address became known while it exists. Owner-only permissions do not stop that account or root, and the private-files web probe does not certify every export address or domain. This is an explicit limit of the private-files promise, not equivalent to encrypted backups.

These are deliberate choices, not oversights. Each makes daily use easier and costs something if a device you use is lost or stolen.

- **Staying signed in.** A browser session lasts 180 days. That suits a calendar you open many times a day. The cost is that anyone holding an unlocked device that is signed in can use your calendar without the password until the session ends or is revoked.
- **Remembered browsers (since 0.2.3).** A browser that has signed in keeps a device cookie for a year, even after you sign out. The cookie never signs anyone in by itself. It only lets a sign-in with the right password through the overall sign-in brake while a distributed attack is going on (issue #59). Someone with the device but not the password gains at most 3 password guesses per 15 minutes while the brake is on. So the remembered browser adds very little to what a lost device already exposes. The open session is the real risk.
- **No permanent account lock.** Wrong passwords slow guessing per address and overall. During a distributed attack, an existing signed-in session still works, and a browser with a valid remembered-device cookie or a recently successful network can sign in. A new browser on a new network can be blocked even with the right password until the attack subsides. Clearing site cookies or using private browsing loses the remembered-browser exemption. Use a long, unique password.
- **CalDAV apps hold a credential.** A phone or desktop calendar app syncing over CalDAV stores whatever you gave it. Give it an API token rather than your password, so a lost device can be cut off by revoking one token instead of changing the password everywhere.

### Email and outside services

Email admission is an owner preference, not proof of sender identity. The default adds events from approved senders and holds other new events for Review; the owner can instead allow any sender or hold everything. Approval can cover an address or domain. A short built-in list forbids broad approval for common shared mail providers, but cannot identify every provider. A forged From address can satisfy an approval. Keep the ingest address private. API keys can change this preference and the approval list, just as they can create events directly. Existing invitation changes and cancellations still require Review; only applied sequences can make pending claims stale.

Malformed mail keeps a durable checkpoint and a separate Review notice until dismissed. Notices retain available sender and subject information independently of receipt pruning. These per-message notices can accumulate until the owner clears them; the ordinary new-event and paid-call limits do not hide unreadable messages. SMTP replies share persistent outbound email admission with notifications. A per-event nonblocking lock prevents concurrent replies, and interrupted attempts require explicit retry confirmation because email and the database cannot commit together. Ranking has separate persistent account and calendar call budgets. Plugin place queries honor the application's lookup setting; trusted native plugin code is not a sandbox.

### If a device is lost or stolen

API keys remain broad account keys. They can configure, enable and run installed plugins and decide duplicates, but cannot mark the worker intentionally off or turn update notices off. Plugin uninstall and run undo, invitation decisions and replies, proposals, automation notice dismissals, account credentials, Google connection management, export, updates and private-file checks require a browser session. Plugin fields declared `secret` are write-only to browser and token callers; native plugin code remains trusted and can use those values. System health gives agents cleaned diagnostic reasons without host paths or notification destinations.

Writes in the credential-sensitive paths recheck the exact session, token or verified password version under the same transaction lock as the change. Google replies and disconnects recheck before the outside request and again in a short locked transaction before saving its result. No database lock is held while contacting Google. Google and the database cannot form one transaction: a reply or revocation already sent may still take effect remotely after local recovery, and an in-flight revocation can invalidate a newly reconnected grant. Settings then says **Reconnect needed** when Google rejects that grant. Notification destinations are rechecked immediately before each send; a provider may still deliver a message already submitted.

Subscriptions added from browsers before this update are owner-confirmed and are not automatically paused. New browser subscriptions record their creator. **Sign out everywhere else** lists subscriptions added by the other browsers, with their name, host and date, and asks whether to keep them running or pause them for Review. Keeping them confirms ownership. A changed list must be reviewed again before anything is changed. Ordinary sign-out and session expiry pause nothing. A password reset pauses newly tracked browser subscriptions for Review; old owner-confirmed subscriptions keep running. Keeping a paused feed requires recent password confirmation and cannot be undone into an older authorization state.

Remote sign-out stops server access, not data already on the device. The phone app keeps its existing offline allowance of up to 24 hours after its last confirmed sign-in, for travel and poor connections. A confirmed revoked session clears private browser caches when the app can contact the server. Remote sign-out cannot erase screenshots, copied data or a device deliberately kept offline; use the device's own lock or remote erase for that.

1. From a device you still have, open Settings, Account and choose **Sign out everywhere else** (since 0.2.4). This signs out every other browser, forgets every other remembered browser, stops push reminders to every other device, gives every public calendar feed created while signed in a new URL, and sends reminder email back to the account address. The browser you use stays signed in. External calendars using an old feed URL need the replacement shown in Better-Cal.
2. On the same page, revoke any API key the lost device held.
3. If you think the password itself was seen, or you have no signed-in device left, reset it on the server: `php server/bin/seed.php --email=you@example.com`. It asks for the new password, then signs out every browser including yours, stops push reminders to every device and forgets every remembered browser. On its own it does not give feeds new addresses or reset the reminder email the way step 1 does. Adding `--revoke-tokens` does those and more: it revokes every API key (and pauses the calendar subscriptions those keys created), gives every outbound feed a new address, sends reminder emails back to the account's own address, pauses every connected Google account and asks Google to revoke its access, and stops unfinished Google moves. Reconnect each Google account under Settings, Connections afterward; cached events stay visible while it is paused.

## Scope notes

- Better-Cal is single-user. There is one login; other people reach it through CalDAV, shared feeds and invitations. Problems that require being that one logged-in user are still worth reporting if they cross a boundary the app is supposed to keep (a feed reaching an internal address, a plugin escaping its calendar, an emailed invitation changing something without a decision).
- Outbound fetches (feeds, geocoding, Google, plugins) go through one HTTP client that refuses private, loopback, link-local and cloud-metadata addresses, checks and pins the address again after every redirect, and ignores proxy settings. Web push is sent separately, only to known browser push services (an operator can add more with `BETTERCAL_PUSH_EXTRA_HOSTS`), over https on port 443 with redirects off. A way around either is a finding.
- Secrets live in the settings file and in the database sealed with libsodium; nothing in this repository should ever hold one. If you see one, that is a finding too. The private-files check is the one outbound request outside that client: it asks only the install's own main domain for its own probe file, with short timeouts and no redirects beyond one that keeps the path.
- A way to read `.env.php`, a backup's contents or the setup code over the web from a server that runs PHP is a finding.
- `server/bin/update.php` must never install a release that isn't signed by a trusted key, or write outside the app's own folders. A way to make it do either is a finding.
- The setup and database update pages must do nothing for someone without the code from `better-cal-code.php`, and setup must never run once settings exist. A way around either is a finding.
