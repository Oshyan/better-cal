# Security

Better-Cal holds a person's calendar, their contacts, and the credentials that reach their Google account and mail. Reports are taken seriously and answered.

## Reporting a vulnerability

Please do not open a public issue for a security problem.

- Preferred: GitHub private vulnerability reporting on this repository (the "Report a vulnerability" button under the Security tab). It stays private until a fix is out.
- Or email coding@oshyan.com.

Include what you found, how to reproduce it, and what you think it allows. You will get a reply within a few days, an honest assessment, and credit in the fix commit if you want it. There is no bug bounty.

Known residuals, accepted and documented rather than fixed:

- **Push reminders to many devices.** An account can register up to 100 devices by default, and the same device counts once. Reminders still go out one device at a time, each with its own timeout, so a long list of unreachable devices can slow delivery; there is no hard cap on the total time. Devices registered before 0.9.87 are kept, even past the limit.
- **Older links during the transition.** New `/add` and `/subscribe` links put private values (a feed's secret address, event details from the browser extension) after a `#`, which browsers never send to the server. An older extension or a webcal handler saved before 0.9.87 still sends them in the visible part of the address, where the server's access log can record it; clearing the address bar afterwards can't undo that. Update the extension to 2.1.1. The part after `#` isn't encrypted: the browser and the page can still read it.
- **Signing in on a new device during an attack.** Someone controlling 10 or more internet addresses (cheap with IPv6) can trigger the overall sign-in brake. While it's on, a password sign-in is refused from an address that hasn't signed in during the last 30 days, unless the browser has signed in here before (it keeps a device cookie, since 0.2.3). CalDAV apps using API keys aren't affected. A brand-new device waits for the attack to stop; a one-time code to let it in is planned (issue #59).
- **AI judgments in batches.** Prompt filters and ranking send events to the model 25 at a time, so text in one event could in principle sway how the model judges the others. Each event goes in as separate, marked data with instructions to judge it on its own, and the answers are checked for exact IDs, one result per event, and valid values. Those checks can't prove the model judged each event independently. Sending events one at a time would cost up to 25 times as much.
- **Shared dev mode.** `DEV_ISOLATION_MODE=shared` deliberately lets the dev copy share the production account, database user and PHP pool, so dev code can reach production files and data. Cleaning the cloned data removes copied credentials but doesn't make a boundary. `strict` is the default; it checks that dev can neither read nor write production ([docs/deploying.md](docs/deploying.md#development-deployments)).
- **Deploying as root.** When the deploy script connects as root, the settings file stays root-owned, but the app account owns the folder it sits in, so that isn't a hard boundary. Deploying as a non-root user with sudo skips that step.

The latest full scan covers the code as of 0.9.86 (2026-10-16); its fixes are in 0.9.87, the re-review's in 0.9.88, and the last review of the changes before 1.0 in 1.0.0. Changes after that have tests and review as they are made, and full scans will continue at regular intervals. Anything you find is worth telling us about.

## Releases and updates

How code reaches an install, and what has to be true before it does.

**What the app does on its own:** once a day it checks GitHub for a newer release and tells you, with a link to its notes. It never downloads or installs code.

**What `server/bin/update.php` checks before installing anything** (it runs only when you run it):

1. The release is a published, non-prerelease, **immutable** GitHub release of this repository, so its tag and files can't be swapped after publishing.
2. Its manifest matches GitHub's SHA-256 digest and the rules the update notice applies (version, priority, a secure-version floor that never moves backwards).
3. **Its signature verifies.** Each release carries `bettercal-release.sig`, a statement of its version, commit and the SHA-256 of its zip and manifest, signed by a key in `server/config/release-keys.php`. The signed hashes must match the files being installed, and in a git checkout the tag must point at the signed commit.
4. The downloaded zip matches GitHub's SHA-256 digest, and it unpacks only into its own folder: no paths that climb out, no symbolic links, bounded in size.

**The signing keys never touch GitHub.** There are two, and either one can sign: a FIDO2 hardware security key that needs its PIN and a touch, which signs every release, and a key file kept in a password manager for recovery. Releases are signed on the maintainer's machine after GitHub builds the zip. So taking over the GitHub account or the build isn't enough to get code onto an install that updates with `update.php`: it also takes one of those keys. Keys can be added or dropped in a release signed by a key already trusted, which is how a lost or exposed key is replaced, and `update.php` says whenever a release does that ([docs/releasing.md](docs/releasing.md#signing)).

**Before anything is signed** (since 0.9.86 and 0.9.87), the maintainer's machine:

- rebuilds the release from the tagged source and the lock file, and checks that GitHub's zip matches it file for file, comparing without unpacking the downloaded copy;
- checks that every PHP library in it matches the Git commit the lock file names;
- checks that the release's manifest (its priority and security floor) is exactly the one it wrote.

The signing program runs from a prepared, pinned environment and downloads nothing while signing. One limit remains: the hardware key protects its secret, but malicious software already on the signing computer could swap what it's asked to sign during a genuine PIN and touch.

**During an update:** one update runs at a time (a database lock, shared by `update.php` and the database update page); the site shows "updating" and the worker pauses (it waits for a running job to finish first); the database is backed up first, by PHP itself; the previous version stays whole beside the new one; and `update.php --rollback` puts both the code and the database back, including after an update that was cut off partway. The newest two previous versions and backups are kept, older ones removed. Backups go in a folder beside the app, readable by its account only, encrypted, with names that can't be guessed. That folder and the previous version's get a deny-all `.htaccess` in case the app sits inside a web root, and the updater warns when it seems to.

**Its own address:** Better-Cal answers only at the host in `BETTERCAL_BASE_URL` and redirects or refuses any other, so files reachable as a folder of another site (`example.com/cal/`, common where hosts store subdomains inside the main web root) can't put it on that site's origin. It needs a domain or subdomain of its own, and a separate hosting user where it shares an account with other sites ([docs/install.md](docs/install.md#choosing-where-to-put-it)). Where a host only lets a subdomain point inside the main site's web root, the private files protect themselves (below), and a `.htaccess` at the top of the app folder refuses every request for anything in it except `server/public` on servers that read one (Apache and LiteSpeed).

**Private files on any host (0.9.83):** every file Better-Cal writes that holds a secret ends in `.php` and starts with `<?php __halt_compiler();`, so a server that runs PHP returns an empty page for it: the settings file (`.env.php`), the one-time setup code, the update record, the private-files check's result and PHP's error log. They're always read as text, never included, so no value can break the guard. Database backups are encrypted with libsodium's secretstream (XChaCha20-Poly1305) under a key derived from the session secret, and a restore checks the whole file before it changes anything. The key comes from the settings file, so encryption protects a backup only while that file stays private: it covers a server that hands out the backups but not the settings. Only `index.php` and `dav.php` run from the web (0.9.82). A self-check asks the install's main domain for a probe file in the app folder and reports in Settings, System whether the settings could be downloaded there ([docs/install.md](docs/install.md#keeping-private-files-private)). The one case none of this covers is a server that hands out `.php` files as text and ignores `.htaccess`; the self-check reports exactly that case as "Fix this now".

**First install:** `server/bin/install.php` writes `.env.php` readable by its owner only, with a freshly generated session secret, and never replaces existing settings.

**Setup and database updates in the browser** (for hosting without a command line): a fresh install with no settings file shows a setup page on every path, and an install whose new files have database changes waiting shows a database update page. Both run before anyone can sign in, so both first ask for a one-time code written to `better-cal-code.php` in the app folder (guarded like the settings file): only someone who can read the server's files gets past the first screen, which keeps a stranger who finds a new install first from setting it up for themselves. The code is 60 bits, expires after an hour and works once: entering it starts a session (an hour, in an HttpOnly, SameSite=Strict cookie, with every form carrying a token derived from it), and entering the same code again doesn't replace that session. Wrong tries never change the code or slow the request, so a stranger sending wrong codes can't lock the owner out or tie up the server. If the browser loses its session, deleting `better-cal-code.php` and reloading gives a new code, and the page says so. The code and its session are stored together in one guarded file, under a lock. Before the code is entered, the page says only which of the two it is (setup, or a database update waiting); over plain HTTP it warns that what's typed travels unencrypted. The pages send a strict Content-Security-Policy and can't be framed. Setup exists only while there are no settings: once it writes `.env.php`, that code path is never reached again, and it refuses a database that already holds an account. The database update backs up first and shows "updating" to everyone else while it runs. If its request is cut off (a host's time limit), the page takes over again, to run it again or restore that backup. While changes wait, or when older files were put back over a database a newer version updated, the API and CalDAV refuse with 503 rather than run against a schema the code wasn't written for.

**Third-party browser code:** the libraries under `web/vendor/` (Preact, htm, Squire, DOMPurify, Leaflet) are the published npm releases, some minified, changed only where [web/vendor/README.md](web/vendor/README.md) says (two one-line edits to Preact's files). Each is pinned by SHA-256 in `web/vendor/manifest.json`, every deploy checks the tree against those pins, and `node scripts/vendor.mjs --check-upstream` re-downloads each release and confirms the committed file matches it. The PHP libraries are pinned in `server/composer.lock` and checked against the Packagist advisory database on every push and deploy.

**Limits, stated plainly:**

- The update notice is signature-checked since 0.9.86: a release is announced, and its security floor recorded, only when its signature verifies. Someone controlling the GitHub account can still hide new releases from installs that haven't seen them yet; nothing signed and time-stamped says how new the newest release is.
- Release notes aren't signed, since GitHub lets them be edited after publishing. `update.php` shows them only after the release's signature checks out, labels them unsigned, and strips characters that could control the terminal.
- In a git checkout, `update.php` checks the tag against the signed commit, but `composer install` then fetches the PHP libraries from Packagist and GitHub, outside the signature. The zip carries them inside it.
- Updating from 0.9.74 to 0.9.75 used the 0.9.74 updater, which predates signatures. From 0.9.75 on, every update is checked.
- A fresh install, or an update uploaded by hand, isn't checked against a signature unless you check it yourself first: files uploaded through a file manager can't vouch for themselves. With no earlier copy to check against, a first install means trusting the download, and a checker taken from inside the same download proves nothing. You can [check a download on your own computer](docs/install.md#optional-verification-before-upload); it needs no SSH on the host.
- On a host without working file locking, setup and the database update page still work, and log the limitation rather than warning on the page. Two requests at the same moment could then trip over each other; a host that quietly ignores locks behaves the same way, and the app can't tell. A used code is still refused.
- On shared hosting, PHP can usually write to the app's own files, so anyone who can run PHP as that account can change the code. That's inherent in this kind of hosting, and why an update needs nothing more than that account.
- The deny-all `.htaccess` files work only on servers that read them; with Nginx, the guard lines and encryption are what protect the private files. The self-check covers the main domain at the place it would serve the folder, not every domain on a hosting account.

## Design trade-offs

These are deliberate choices, not oversights. Each makes daily use easier and costs something if a device you use is lost or stolen.

- **Staying signed in.** A browser session lasts 180 days. That suits a calendar you open many times a day. The cost is that anyone holding an unlocked device that is signed in can use your calendar without the password until the session ends or is revoked.
- **Remembered browsers (since 0.2.3).** A browser that has signed in keeps a device cookie for a year, even after you sign out. The cookie never signs anyone in by itself. It only lets a sign-in with the right password through the overall sign-in brake while a distributed attack is going on (issue #59). Someone with the device but not the password gains at most 3 password guesses per 15 minutes while the brake is on. So the remembered browser adds very little to what a lost device already exposes. The open session is the real risk.
- **No permanent account lock.** Wrong passwords slow guessing per address and overall. During a distributed attack, an existing signed-in session still works, and a browser with a remembered-device cookie or a network that recently signed in can sign in. A new browser on a new network can be blocked even with the right password until the attack stops. Clearing site cookies or using private browsing loses the remembered-browser exemption. Use a long, unique password.
- **CalDAV apps hold a credential.** A phone or desktop calendar app syncing over CalDAV stores whatever you gave it. Give it an API key rather than your password, so a lost device can be cut off by revoking one key instead of changing the password everywhere.

### Backups and exports

**Backups need the session secret.** New database backups are always encrypted with a key made from `BETTERCAL_SESSION_SECRET`, so without one Better-Cal refuses to back up rather than write a plain copy. Settings, System warns when it's missing and shows a line to add to `.env.php`; the database update page offers the same before an update. Better-Cal never writes the setting itself. If a secret you had was lost, put the original back instead: a new one makes older encrypted backups and saved service credentials unreadable. Plain backups from before encryption can still be restored, after a confirmation: the database update page asks first, and `update.php --rollback` needs `--allow-plain`, because nothing shows whether a plain backup was changed. A restore opens the backup once and reads every pass from that one handle, refusing a link, a hard-linked file, or a file swapped in while it was opened. On hosts without PHP's POSIX extension it also refuses a backup folder whose parents another account's group could write; fix the folder permissions and retry.

**Backup folders must be what they claim.** Every backup folder and file must be a real directory or a regular file owned by the account running Better-Cal, with no symbolic or hard links. That's checked before anything is changed, encrypted, written or removed. Converting older backups should be done as the account that owns them, not as root. None of this protects against malicious code already running as the same account, or a host administrator.

**Shared folders on the way.** Folders above the private storage may be writable by their group when that group is the app account's own, as is normal on Linux hosting. Better-Cal can't prove nobody else belongs to that group, so it trusts the host to keep it private, and without PHP's POSIX functions it leaves group checks to the host entirely. A folder anyone can write to is refused unless it's a shared temporary folder protected by the sticky bit. Root still refuses any folder owned by another account.

**Restores wait for the worker.** A restore takes the same locks as an update. If the worker is mid-job, the restore changes nothing and offers to try again. If a restore fails or is cut off, the site stays closed, with a button on the database update page to run it again. These protections rely on the host's file ownership and MySQL's named locks working normally.

**Exports are complete, never cut short.** Exports need a signed-in browser and have no event limit. A single calendar streams straight to the download in batches. "Export everything" builds one file per calendar plus the zip in `.runtime-cache/exports`, readable by the app account alone and named with 128 random bits, then downloads the finished zip and deletes the files, even on failure. One export runs at a time. A broken single-calendar download ends without its closing line and should be downloaded again. Memory use stays small however large the account; disk space and the host's time limits can still stop an export, and nothing is quietly dropped to make it fit.

**Export files aren't encrypted.** Unlike backups, the temporary export files are plain. On a host misconfigured to serve `.runtime-cache` publicly, someone who learned a file's random name could fetch it in the seconds it exists. Keep that folder out of anything the web server serves, or blocked; the private-files check doesn't test export addresses.

### Email and outside services

**Which emailed events get added is your choice, not proof of who sent them.** By default, events from senders you've approved are added and others wait in Review; you can instead accept any sender, or hold everything. An approval covers an address or a whole domain, except for well-known shared mail providers (Gmail, Outlook and the like), which can only be approved address by address; the built-in list of those can't name every provider. Anyone can forge a From address, so someone who knows your ingest address and guesses an approved sender can still get an event added. Keep the ingest address private. API keys can change this setting and the approved list, as they can already add events directly. Changes and cancellations to invitations already on your calendar always wait in Review, and only versions you've accepted can make a waiting one out of date.

**Unreadable email stays visible.** An email Better-Cal can't read gets its own notice in Review, with whatever sender and subject it could make out, kept until you dismiss it, even after the 90-day mail log moves on. These can pile up until you clear them, since the limits on new events and paid AI calls don't hide them.

**Replies and outside calls.** Invitation replies count against the same outgoing-email limits as notifications, and only one reply per event can be sending at a time. If sending was interrupted, Better-Cal asks before trying again, because it can't know whether the first attempt arrived. Ranking has its own AI call budgets per account and per calendar. Plugins obey the place-lookup setting, but plugin code itself is trusted, not sandboxed.

### API keys and revoking access

**API keys are broad on purpose.** A key can do most of what a signed-in browser can, so an agent can be genuinely useful: events, calendars, people, settings, and configuring, enabling and running installed plugins. A key can't mark the worker as off on purpose or turn update notices off, since those are how you'd notice something wrong. Some things always need a signed-in browser: uninstalling a plugin or undoing its run, deciding or answering invitations, proposals, dismissing automation notices, keys and sessions themselves, connecting Google, exporting, updates and the private-files check. Plugin settings marked `secret` can be set but never read back, by anyone; the plugin's own code is still trusted with them. The health page shows keys the state of things and cleaned-up error reasons, without server paths or where alerts go.

**Revoking takes effect at the moment of the change.** Every sensitive change rechecks that the session, key or password is still valid, inside the same database transaction that saves it, so a request already in progress can't finish after you revoke access. Google is the exception, since Google and the database can't commit together: a reply or disconnect is rechecked before contacting Google and again before saving the result, without holding a lock during the call. A reply or revocation already sent to Google can still take effect, and a disconnect in progress can cancel a connection you've just made again; Settings then says **Reconnect needed**. Notifications recheck their destination right before each send, but a message already handed to a provider can still arrive.

### If a device is lost or stolen

What to do:

1. From a device you still have, open Settings, Account and choose **Sign out everywhere else** (since 0.2.4). This signs out every other browser, forgets every other remembered browser, stops push reminders to every other device, gives every public calendar feed created while signed in a new URL, and sends reminder email back to the account address. The browser you use stays signed in. External calendars using an old feed URL need the replacement shown in Better-Cal.
2. On the same page, revoke any API key the lost device held.
3. If you think the password itself was seen, change it in Settings, Account, **Change password** (it needs the current one). Every browser signs out and yours signs straight back in. Leaving **Also sign out everything else** ticked does what `--revoke-tokens` does below, and plugins an API key had turned on go to Review. If you have no signed-in device left, reset it on the server: `php server/bin/seed.php --email=you@example.com`. It asks for the new password, then signs out every browser including yours, stops push reminders to every device and forgets every remembered browser. On its own it does not give feeds new addresses or reset the reminder email the way step 1 does. Adding `--revoke-tokens` does those and more: it revokes every API key (and pauses the calendar subscriptions those keys created), gives every outbound feed a new address, sends reminder emails back to the account's own address, pauses every connected Google account and asks Google to revoke its access, and stops unfinished Google moves. Reconnect each Google account under Settings, Connections afterward; cached events stay visible while it is paused.

**Subscriptions added from other browsers.** Since 0.9.87, Better-Cal records which browser added each calendar subscription. **Sign out everywhere else** lists the ones added from the browsers you're signing out (name, the feed's host, the date), and asks whether to keep them running or pause them for Review. Keeping them confirms they're yours. Sign-out always goes through. If a subscription is added, or one is pointed at a different address, after you open the list, it's paused whichever you chose, and the result says so. Renaming one changes nothing. Ordinary sign-out and sessions expiring on their own pause nothing. Subscriptions from before 0.9.87 count as yours and are never paused automatically. A password reset pauses browser-added subscriptions for Review; keeping one asks for your password again.

**Data already on the device.** Signing a device out stops it reaching the server, but not what it already holds. The phone app keeps working offline for up to 24 hours after it last confirmed it was signed in, for travel and poor signal, and clears its saved data as soon as it reconnects and learns it was signed out. Nothing can erase screenshots, copied data or a device kept offline on purpose; use the device's own lock or remote erase for that.

## Scope notes

- Better-Cal doesn't track security problems in PHP, the database, the web server or the operating system. Keeping those updated is up to whoever runs the server, through their host or their distribution. If that's you, subscribe to your distribution's security announcements ([Debian](https://lists.debian.org/debian-security-announce/), [Ubuntu](https://ubuntu.com/security/notices)) and [PHP's announcement list](https://www.php.net/mailing-lists.php).
- Better-Cal is single-user. There is one login; other people reach it through CalDAV, shared feeds and invitations. Problems that require being that one logged-in user are still worth reporting if they cross a boundary the app is supposed to keep (a feed reaching an internal address, a plugin escaping its calendar, an emailed invitation changing something without a decision).
- Outbound fetches (feeds, geocoding, Google, plugins) go through one HTTP client that refuses private, loopback, link-local and cloud-metadata addresses, checks and pins the address again after every redirect, and ignores proxy settings. Web push is sent separately, only to known browser push services (an operator can add more with `BETTERCAL_PUSH_EXTRA_HOSTS`), over https on port 443 with redirects off. A way around either is a finding.
- Secrets live in the settings file and in the database sealed with libsodium; nothing in this repository should ever hold one. If you see one, that is a finding too. The private-files check is the one outbound request outside that client: it asks only the install's own main domain for its own probe file, with short timeouts and no redirects beyond one that keeps the path.
