# Two questions asked of real Google before the conflict choice (2026-11-14)

Asked by hand for 1.5.7, through Google Calendar's own page and a 1.5.6 install connected to an empty test calendar the account owns. Every event was invented, dated in March 2027, had no guests, and was deleted when its question was answered; the calendar was empty again at the end. The write-up says what was seen, in general terms.

## P2: do notes nobody changed compare as the same after a round trip?

**Why it was asked.** The conflict choice compares three values of each field: what Better-Cal held, what Google holds now, and what the change would put there. If Google handed back notes in a different spelling each time it was read or written, every change to an event with notes would ask about notes nobody touched, and the simple equality (the two strings are the same) would need a normaliser.

**What was done.** Two events were written in Google's page. One had notes with bold, an ampersand, a line break, a non-breaking space and a web address. The other had plain notes with an ampersand and a line break. Then, from the install: a poll, a second poll, a change of title only followed by a poll, the same notes sent back unchanged followed by a poll, and three new sets of notes written from the install (formatted with a link and a non-breaking space, plain with blank lines, and text holding character entities), each followed by a poll.

**What was seen.**

- Notes with formatting arrive as HTML: `<b>`, `<br>`, `&amp;` for the ampersand. Plain notes arrive as plain text: a bare `&` and a newline character. So the same ampersand has two spellings depending on whether the notes hold any formatting. That is a difference between two events, not between two reads of one event.
- Google's editor moved the non-breaking space: the one typed between two words came back as an ordinary space, and one appeared after the bold run where none was typed. Once saved, it stayed where Google put it.
- A web address typed into Google's editor is shown there as a link but is stored as bare text, with no anchor.
- Every later read of the same event gave the same string: after a second poll, after a change of title sent from the install, after the same notes were sent back, and after Google's own editor saved the event with a different field changed (see P3).
- Notes written from the install are stored there as cleaned HTML (a bare ampersand becomes `&amp;` when the notes hold formatting, a link gains its safety attributes), and what the next poll read from Google was the same string, in all three cases.

**Answer.** Yes. Unchanged notes compare as the same by plain string equality across polls and across writes in both directions. No normaliser is needed for the round trip, and 1.5.7 builds none. What plain equality will not see as the same is a person retyping notes at Google so that they look alike and are spelled differently (the moved non-breaking space is the example); that asks one question more than strictly needed, which is the direction the owner chose.

**Limits of the answer.** One account, one day, Google's web editor only. Notes written by Google's phone apps or by another calendar program through Google were not tried.

## P3: when a single event is made repeating at Google, does it keep its id?

**Why it was asked.** The model refuses a change to a single event that became a repeating one at Google, with its own sentence. That only works if the event can still be recognised as the same one.

**What was done.** The first event above, a single event, was opened in Google's editor, set to repeat weekly, and saved. Then the install polled.

**What was seen.**

- The event kept its id. Before the change the editor's address carried the event's id; afterwards the same event's address carried that id followed by the day's instant, which is how Google names one day of a series whose id is the first part.
- The install kept the same row with the same iCalUID, now marked as repeating and carrying the weekly rule, and showed the following weeks. No second row appeared and nothing was removed.
- The notes of the event were unchanged by Google's editor saving it.

**Answer.** Yes on both counts: the id and the iCalUID stay, and the event read back by them carries the rule. A single event made repeating at Google can be recognised and refused by the sentence the model gives it.

## Clean-up

The series was deleted in Google's page (all events) and the remaining single event after it. A last poll left the test calendar with no events in the install.
